# 배율과 터미널 한글 조합 박스 (Windows)

대상: 기준 b89dde7, 커밋하지 않은 변경 (`src/zoom.ts`, `src/selftest.ts`, `scripts/selftest-plan.json`, `docs/spec.md`,
`docs/windows-plan.md`).

## 문제와 원인

Windows에서 앱 배율이 1이 아니면 터미널에서 한글을 조합할 때 박스(`.composition-view`)가 커서에서 어긋났다.

실측 (자체 테스트 단계로 잼, 디스플레이 배율 1.5):

| 앱 배율 | 실제 devicePixelRatio | 덮어쓴 값 | xterm 칸 폭 | 그려진 칸 폭 |
|---|---|---|---|---|
| 1 | 1.5 | 1.5 | 6.67 | 6.66 |
| 1.5 | 2.25 | 3.375 | 6.81 | 10.22 |

WebView2(Chromium)는 배율을 devicePixelRatio에 이미 넣는다. `zoom.ts`가 WKWebView 기준으로 배율을 한 번 더 곱해서,
xterm이 아는 칸 폭과 캔버스에 그려진 칸 폭이 배율만큼 달랐다. 조합 박스는 `커서 열 × xterm 칸 폭`에 놓인다.

## 수정

- `src/zoom.ts`: Chromium(`devicePixelContentBoxSize`가 있음)에서는 devicePixelRatio를 덮어쓰지 않는다.
  `screenPixelRatio`는 배율을 뺀 값을 돌려준다. WebKit은 그대로.
- 자체 테스트 `zoomIme`: 1.5·0.8배에서 칸 폭이 그려진 대로인지, 조합 박스가 커서 자리인지 본다. 보기 메뉴 클릭은 맥에만
  있어 웹뷰 배율을 직접 바꾼다.

확인: Windows에서 `zoomIme` 통과, 수정을 끄면 두 배율 모두 실패 (1.5배: 칸 폭 6.81 대 10.22). tsc, `selftest-changed --check` 통과.
맥 실행은 확인하지 못했다 (Windows에서 `selftest.sh`가 돌지 않음).

## 리뷰 지적

### R1 (P3) 기존 `testZoom`의 CSS 해상도 검사가 WebKit 전제

판단: 타당. `src/selftest.ts`의 "배율: CSS 해상도는 실제 화면 비율을 따름" 검사는 덮어쓴 devicePixelRatio의 쿼리가 안 맞는다고
본다. Chromium에서는 덮어쓰지 않으므로 이 검사는 맞지 않는다.

수정하지 않음: `testZoom`은 맥에만 있는 메뉴 클릭(`selftest_click_menu`)을 써서 Windows에서 돌지 않는다 (실행 결과
`Command selftest_click_menu not found`). 맥에서는 이번 변경으로 동작이 바뀌지 않는다. Windows 자체 테스트를 옮길 때
(`docs/windows-plan.md`의 남은 것) 함께 맞춘다.
