## 1. [P1] 부모 폴더의 링크를 따라 worktree 밖에 씀 (`prepare.rs`) — 타당, 수정 (범위를 넓혀)

**검증**: 소스·재현. 쓸 자리의 부모가 디렉터리인지만 봤다. 원본의 `config`는 일반 폴더이고 새 worktree의 `config`가
밖을 가리키는 링크면 `config/.env`가 밖에 복사됐다. 같은 구멍이 비밀 파일 말고도 있었다: 폴더 복제(`renamex_np`가 그
부모 링크를 따라 밖에 옮김), 가상 환경 만들기, 설치 명령을 돌리는 폴더.

**수정**: `place_inside` — 쓸 자리의 부모를 실제로 따라간 경로(`canonicalize`)가 그 worktree의 실제 경로 안이고, 그 자리가
링크가 아니어야 한다. 가져오기의 모든 종류(복사·새로 만들기·복제)에 앞서 본다. 설치는 그 폴더를 실제로 따라간 곳이
worktree 안이어야 돌린다. 복제 엔진(`clone_tree`)도 놓일 자리의 실제 부모가 worktree 밖이면 만들지 않는다 (이중 확인).

**확인**: `never_writes_through_a_linked_parent` (비밀 파일, 폴더 복제, 설치가 모두 실패하고 밖의 폴더는 비어 있음).
확인을 끄면 실패.

## 2. [P1] 비밀 파일 복사가 실패하면 반쪽 파일과 넓은 권한이 남음 (`prepare.rs` → `clone.rs`) — 타당, 수정

**검증**: 소스·재현. 제자리에 기본 권한(0644)으로 만들고 쓴 뒤 권한을 바꿨다. 크기 제한으로 쓰기를 끊으면 0600·8,205바이트
원본이 0644·4,096바이트로 남았고, 다시 하면 "있음"으로 넘어갔다.

**수정**: `clone.rs`의 `copy_file_into`. ddak 폴더에 실행마다 고유한 임시 파일을 처음부터 0600으로 만들고(`create_new`),
다 쓰고 `sync_all` 한 뒤 원본 권한·수정 시각으로 하고 `renamex_np(RENAME_EXCL)`로 옮긴다 (덮어쓰지 않음). 실패하면 임시
파일을 지운다. 끊긴 실행의 임시 파일은 다음 실행의 정리가 지운다 (`remove_tree`가 파일도 지우게 했다).

**확인**: `file_copy_is_all_or_nothing`. 테스트 전용 장치로 4,096바이트 뒤에 쓰기가 실패하게 하면 제자리에도 ddak 폴더에도
아무것도 없고, 다시 하면 8,205바이트·0600으로 복사된다. 제자리에 바로 쓰는 옛 방식으로 바꾸면 실패.

## 3. [P2] 실패한 Node 설치를 다시 하지 않음 (`prepare.rs`) — 타당, 수정

**검증**: 재현. `node_modules`가 있으면 건너뛰었는데, 실패한 `npm ci`도 `node_modules`를 남긴다.

**판단**: 폴더만으로는 성공한 복제·설치와 실패하고 남은 것을 구분할 수 없다. 앞선 복제 리뷰에서는 틈 자체를 없앴지만
(제자리에 확인을 마친 것만 나타나게), 설치 명령은 그 자리에서 돌아 그렇게 할 수 없다. 리뷰어가 앞서 제안한 진행 기록을 쓴다.

**수정**: 작업그룹마다 ddak 폴더에 진행 기록 `.ddak-state-<작업그룹>.json` (`started`·`done`, 옆에 쓰고 옮김). 복제가 성공하면
`clone:<경로>`, 설치가 성공하면 `install:<폴더>\n<명령>`을 적는다. Node 설치는 `node_modules`가 있고 그것이 우리 복제나 그 설치의
성공으로 생긴 것일 때만 건너뛴다. 그 밖에는 다시 돌린다 (`npm ci`는 남은 것을 지우고 다시 받는다).
복제에서 "이미 있음"인 것은 기록하지 않는다 (실패한 설치가 남긴 것일 수 있다).

**확인**: `node_install_reruns_unless_node_modules_is_ours` (기록 없는 `node_modules` → 돌림, 실패는 실패로, 성공 뒤 같은 설치는
건너뜀, 복제한 `node_modules`면 건너뜀). 기록 확인을 끄면 실패.

## 4. [P2] 가상 환경 만들기 실패도 다시 하기에서 성공으로 넘김 (`prepare.rs`) — 타당, 수정

**검증**: 재현. 폴더가 있으면 "있음"으로 넘겼다. 폴더를 만든 뒤 실패하는 Python이면 `bin/python`도 없는 환경이 남았다.

**수정**: `python -m venv`는 만드는 곳의 경로를 안에 박아서 다른 곳에 만들어 옮길 수 없다. 그래서 3번의 기록을 쓴다: 만들기 전에
`venv:<경로>`를 시작으로 적고, 성공하면 마침으로 바꾼다. 다시 할 때 폴더가 있고 시작만 적혀 있으면 우리가 만들다 실패·중단한
것이라 지우고(1번 확인을 거친 자리) 다시 만든다. 기록에 없는 폴더는 누가 만든 것인지 모르므로 그대로 둔다.

**확인**: `venv_retry_replaces_our_unfinished_venv` (폴더를 만들다 종료 코드 9로 끝나는 가짜 Python → 다시 하면 남은 파일이
없어지고 새로 만들어짐, 마친 것과 기록에 없는 폴더는 그대로). 남은 폴더 정리를 끄면 실패.

## 5. [P2] 가상 환경 이름이 설치 명령으로 해석됨 (`setup.rs`) — 타당, 수정

**검증**: 소스·재현. 제안 명령에 가상 환경 이름을 그대로 붙였다. `env$(touch injected)`는 명령 치환이 실행됐다.

**수정**: `shell_word` — 안전한 글자뿐이면 그대로, 아니면 작은따옴표로 감싼다 (`'`는 `'\''`).

**확인**: `shell_words_are_inert` (공백, `$(…)`, `'`, `;`, 백틱 이름을 `sh -c`로 돌려 그대로 나오고 아무 파일도 생기지 않음).
인용을 끄면 실패.

## 후속 리뷰: 진행 기록 2건 — 타당, 수정

### [P1] 시작 기록만 보고 사용자가 만든 가상 환경 폴더를 지움

**검증**: 재현 (리뷰어 기록과 같음). 없는 Python이면 폴더를 만들지 못하고 시작 기록만 남는다. 그 자리에 사용자가 폴더와
파일을 만들면 다시 하기가 "earlier attempt"로 보고 지웠다. 시작 기록은 그 자리의 폴더가 우리 것이라는 근거가 못 된다.

**수정**
- 폴더를 우리가 직접 만들고(`create_dir`), 그 식별자(dev, inode, 만든 시각)를 기록한 뒤 그 안에 `python -m venv`를 돌린다.
  비어 있는 기존 폴더에도 만들어지고 inode는 그대로임을 실험으로 확인했다.
- 실패하면 그 자리에서 (식별자가 맞을 때) 바로 지우고 기록도 지운다. 보통의 실패는 아무것도 남기지 않는다.
- 다시 할 때 폴더가 있으면: 마침 기록이 있으면 그대로 둔다. 적어 둔 식별자와 같으면 끊긴 우리 것이라 지우고 다시 만든다.
  우리가 만들지 않은 것은 지우지 않는다. 완성된 환경(`pyvenv.cfg`와 `bin/python`)이면 그대로 쓰고, 아니면
  "지우고 다시 준비하라"고 알리고 멈춘다. 폴더를 만든 직후 기록하기 전에 끊긴 경우(빈 폴더, 기록 없음)도 여기로 와서,
  예전처럼 성공으로 넘기지 않는다.

**확인**: `venv_only_removes_the_folder_it_made`. 실패 → 폴더 없음. Python 없음 → 사용자가 만든 폴더·파일이 다시 하기 뒤에도
그대로이고 실패로 알림. 사용자가 만든 완성 환경은 그대로. 식별자를 적은 남은 폴더는 지우고 다시 만듦. 식별자 확인을 끄면
실패.

### [P2] 다시 설치하다 실패해도 예전 성공 기록이 남음

**검증**: 재현. 설치 성공 → `node_modules` 지움 → 다시 설치 실패(남은 `node_modules`) → 다음에 예전 성공 기록을 보고 건너뛰고
0으로 끝났다.

**수정**: 설치를 돌리기 전에 그 설치의 성공 기록과 그 폴더 `node_modules`의 복제 기록을 지우고, 성공한 뒤에만 다시 적는다.

**확인**: `failed_reinstall_clears_the_old_success` (위 순서 뒤 다시 설치를 돌리고 실패를 알림). 기록 지우기를 끄면 실패.
