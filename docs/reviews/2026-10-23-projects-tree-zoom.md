# 리뷰 대응: 프로젝트 목록 · 저장소 추가 · 파일 트리 · 화면 배율 (2026-10-23)

리뷰 범위: `dec544b` 이후 커밋 전 작업 트리. P2 5건 모두 타당, 수정.

## 1. 늦게 끝난 초기 로드가 목록을 덮어씀 (`useProjects.ts`) — 타당, 수정

**지적**: 로드 효과에 취소 처리가 없어 StrictMode의 두 번째 효과 실행과 겹치면, 늦게 끝난 로드가 그 사이 추가한
프로젝트를 덮어쓴다. 두 번째 로드가 실패하면 첫 로드로 `loaded=true`인 채 목록이 `[]`가 되어 빈 목록을 저장한다.

**검증**: 소스 확인. 효과가 정리 함수를 돌려주지 않고, 성공·실패 콜백 모두 무조건 상태를 바꾼다.
React StrictMode(개발 빌드)는 효과를 두 번 실행한다. 지연 주입 실험은 리뷰 쪽 결과를 근거로 삼고 따로 재현하지 않았다
(응답 지연을 앱 안에서 만들 수단이 없음).

**수정**: `alive` 플래그. 정리된 효과의 결과는 성공·실패 모두 버린다.

## 2. 감시 해제가 등록보다 먼저 처리되면 감시가 남음 (`FileTree.tsx`) — 타당, 수정

**지적**: 정리 함수가 `fs_watch` 완료를 기다리지 않고 `fs_unwatch`를 보낸다. IPC 도착 순서는 보장되지 않는다.

**검증**: `tauri-2.12.5/scripts/ipc-protocol.js:37` — `invoke`마다 `fetch(ipc://…)`를 따로 보낸다. 요청 사이의
순서를 맞추는 장치가 없다. 내가 `watch.rs`에 적었던 "동기 명령이라 메인 스레드에서 차례대로"는 처리 순서이지
도착 순서가 아니므로 근거가 되지 않는다.

**수정**: 등록 promise를 들고 있다가 등록이 성공한 뒤에만 해제를 보낸다. 등록이 실패했으면 해제하지 않는다.

**확인**: 기존 "펼친 폴더만 감시 / 접으면 감시 해제" 자체 테스트 통과. 순서가 뒤집히는 상황 자체는 자체 테스트로
재현하지 못했다.

## 3. DPR 덮어쓰기가 xterm의 모니터 변경 감지를 깨뜨림 (`zoom.ts`) — 타당, 수정

**지적**: xterm은 `resolution: <dpr>dppx` 미디어 쿼리로 모니터 변경을 감시한다. CSS 해상도는 JS getter와 무관해서
덮어쓴 값의 쿼리는 늘 안 맞고, 모니터를 옮겨도 알림이 없다.

**검증**
- xterm 소스 `CoreBrowserService.ts`: `matchMedia(\`screen and (resolution: ${devicePixelRatio}dppx)\`)`에
  listener를 걸고, 그와 별도로 창 resize 때 `devicePixelRatio`를 다시 비교한다.
- **실험** (자체 테스트 안, 배율 1.1): `real=1 dpr=1.1 match(1dppx)=true match(1.1dppx)=false`.
  CSS 해상도는 실제 값을 따른다 → xterm이 건 쿼리는 처음부터 안 맞아 바뀔 일이 없다.

**수정**: 실제 화면 비율로 쿼리를 따로 걸고, 바뀌면 `resize` 이벤트를 보내 xterm이 `devicePixelRatio`를 다시 읽게
한다. 그 뒤 새 비율로 쿼리를 다시 건다.

**확인**: 자체 테스트에 "CSS 해상도는 실제 화면 비율을 따름" 확인 추가. **실제 모니터 이동은 확인하지 못함**
(이 환경에 모니터가 하나). resize 이벤트로 xterm이 다시 그리는 경로는 배율 테스트(캔버스 해상도)가 확인한다.

## 4. 목록 파일 읽기 실패 후 저장되지 않는 변경을 정상처럼 보여 줌 (`App.tsx`) — 타당, 수정

**지적**: 읽기 실패로 `loaded=false`인데도 추가가 되고, `setError(null)`이 오류 표시를 지운다. 저장은 0회.

**검증**: 소스 확인. `add`가 `loaded`를 보지 않고, 읽기 오류와 추가 오류가 같은 `error` 상태를 쓴다.
수정 전 코드로 아래 자체 테스트를 돌리면 "추가해도 목록이 바뀌지 않음", "오류가 지워지지 않음"이 실패한다 (확인함).

**수정**
- 읽기 오류를 `loadError`로 따로 둔다. 다른 오류로 지워지지 않고 계속 보인다 (`sidebar.loadFailed`).
- 이 상태에서는 추가(`StoreBroken`)·제거를 하지 않고, 추가 버튼을 비활성화한다.

**확인**: 자체 테스트 `corrupt` 시나리오 (깨진 `projects.json`으로 시작). 오류 표시, 버튼 비활성, 추가해도 목록 그대로,
오류 유지, 파일을 덮어쓰지 않음.

## 5. 한글 조합 확정 Enter가 파일 생성을 실행 (`FileTree.tsx`) — 타당, 수정

**지적**: `isComposing=true`인 Enter에도 `fs_create`가 불린다.

**검증**: 소스 확인. `onKeyDown`이 조합 상태를 보지 않는다. 수정 전 코드로 아래 자체 테스트가 실패한다 (확인함).

**수정**: `isComposing` 또는 `keyCode === 229`이면 무시한다 (WebKit은 조합 중 키에 229를 준다).
같은 문제가 있는 저장소 추가 창(폼 Enter 제출, Esc 닫기)에도 같은 처리를 했다 (리뷰 범위 밖, 같은 종류).

**확인**: 자체 테스트 — `isComposing` Enter와 keyCode 229 Enter 모두 만들지 않고 입력란 유지, 조합이 끝난 뒤
Enter로 한글 이름 파일 생성.

- `scripts/selftest.sh`가 앱을 시나리오별로 따로 띄운다: `main`(기존 전체), `restart`(저장된 목록에 없어진 폴더가

  끈 부분(`loaded` 검사)은 `main`과 관계없는 경로다. 이후 수정 상태로 5회 연속 전체 통과, 재현 안 됨.
