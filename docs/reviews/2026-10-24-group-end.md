# 리뷰 대응: 작업그룹 끝내기 (2026-10-24)

리뷰 범위: `fc7cb66` 이후 커밋 전 작업 트리 (`worktrees.rs` 만든 기록·`group_status`·`group_end`, `EndGroupDialog.tsx`).
P1 세 건 모두 타당, 수정. 리뷰어 재현 기록에서 실제로 데이터가 지워졌다. 테스트마다 수정을 잠시 끄고 실패하는 것을 확인했다.
지우는 기능이라 원칙을 "아는 것만 지우고, 모르거나 덜 된 것이 있으면 아무것도 지우지 않고 멈춘다"로 바꿨다.

## 1. [P1] 확인하지 않은 파일·폴더까지 재귀 삭제

**검증**: 소스·재현. 마지막 정리가 남은 것이 링크뿐이라고 보고 `remove_dir_all`을 불렀다. 지워진 것: 작업그룹 맨 위에 새로
만든 메모와 폴더, 기록 없는 작업그룹에서 지금 프로젝트 모양으로 짐작해 빠진 worktree(원본에서 연결을 끊은 저장소)의 커밋
안 한 파일, `.git`이 없어진 worktree의 파일("이미 지움"으로 봤다).

**수정**
- 끝내기 전에 작업그룹 폴더를 본다: 끝낼 worktree, 우리가 만든 링크(원본의 같은 이름 항목을 가리키는 심볼릭 링크),
  `.DS_Store`만 허용. 그 밖의 항목이 있으면 `unknown`으로 멈춘다 (짐작에서 빠진 worktree도 여기에 걸린다).
- worktree 자리는 있는데 `.git`이 없거나 git이 worktree로 보지 않으면 "이미 지움"이 아니라 `incomplete`로 멈춘다.
  "이미 지움"은 자리 자체가 없을 때만.
- 마지막 정리는 우리가 만든 링크와 `.DS_Store`만 지우고 `remove_dir`(빈 폴더만)로 끝낸다. 그새 다른 것이 생겼으면 남기고
  `leftover`로 알린다.

**확인**: Rust `end_keeps_everything_it_does_not_know` (메모·폴더 → unknown, `.git` 없는 worktree → incomplete, 기록 없는
작업그룹에서 프로젝트에서 뺀 저장소의 worktree → unknown. 모두 아무것도 지우지 않음). 모르는 항목 검사를 끄거나 불완전 판정을
"이미 지움"으로 되돌리면 실패. 자체 테스트: 작업그룹 폴더에 메모를 두면 창에 보이고 끝낼 수 없음.

## 2. [P1] detached HEAD에서 만든 커밋을 잃음

**검증**: 재현. 상태는 기록한 브랜치만 봐서, worktree를 detached HEAD로 바꿔 만든 커밋이 "병합 안 된 커밋 0개"로 나왔고
끝내기가 성공했다. 그 커밋은 닿을 수 없게 되어 GC 뒤 사라졌다.

**수정**: worktree의 실제 HEAD에서 어느 브랜치에도, 원본 HEAD에도 없는 커밋 수를 센다
(`rev-list --count <worktree HEAD> --not --branches HEAD`). 하나라도 있으면 `unsaved`로 멈추고 브랜치를 만들어 두라고 알린다.

**확인**: Rust `end_refuses_commits_on_no_branch` (detached 커밋 → unsaved 1로 거부, `git branch saved` 뒤 끝내고 그 브랜치는
남음). 검사를 끄면 실패.

## 3. [P1] 다른 worktree에서 사용 중인 브랜치를 지움

**검증**: 재현. `update-ref -d`는 git의 체크아웃 보호를 거치지 않아, 원본이 체크아웃한 우리 브랜치를 지우고 원본 HEAD를 깨뜨렸다.

**수정**: `git branch -d`로 지운다. git이 원본 HEAD에 병합 안 된 브랜치와 다른 worktree(원본 포함)에 체크아웃된 브랜치를
거부한다. 지우지 못하면 남기고 이유("병합 안 됨", "다른 곳에서 체크아웃 중", "이전 버전에서 만듦")와 함께 알린다.

**확인**: Rust `end_keeps_branch_checked_out_elsewhere` (원본이 체크아웃한 우리 브랜치는 inUse로 남고 원본 HEAD 그대로).
`update-ref -d`로 되돌리면 실패.

## 판단 기준에 대한 리뷰어 의견

- 원본의 지금 HEAD 기준 병합: 제품 정책과 맞다. 원격 병합·squash 병합과 다르다는 점을 스펙에 적었다.
- 기록 없으면 브랜치 보존: 브랜치에는 보수적이지만 작업 파일은 못 지켰다 → 1번의 모르는 항목 검사로 지킨다.
- 일부 삭제 뒤 다시 하기: 리뷰어 실험에서 정상 동작.

## 후속 리뷰: P1 두 건, P2 한 건 — 모두 타당, 수정

리뷰어 독립 재현 기록에서 셋 모두 실제로 커밋이나 브랜치를 잃었다. 소스와 실험으로도 맞다. 테스트마다 수정을 끄고 실패하는
것을 확인했다.

### [P1] git 검사 실패를 안전한 0으로 봄

**검증**: 소스·실험. 커밋 수 검사가 `git(...).ok()...unwrap_or(0)`이었다. 원본에서 `git checkout --orphan empty`를 하면
`rev-list --count <HEAD> --not --branches HEAD`가 128로 끝난다(`ambiguous argument 'HEAD'`). 그런데 0으로 보고 worktree를
지웠다. 커밋 안 한 변경 수(`git status`)도 같았다.

**수정**: 상태 검사(`status_of`)가 `Result`를 돌려준다. 다음을 확인하지 못하면 `git` 오류로 멈춘다.
- 커밋하지 않은 변경 수
- worktree HEAD
- 브랜치에 없는 커밋 수
- 병합 안 된 커밋 수

기록한 브랜치를 사용자가 지운 경우는 먼저 있는지 보고 0으로 둔다 (지울 것도 셀 것도 없음). 실패하는 쪽이 멈추는 쪽인 판정은
그대로 둔다: worktree인지 보는 `rev-parse`가 실패하면 `incomplete`로 멈춘다.

**확인**: Rust `end_stops_when_a_check_fails`. detached 커밋을 만든 뒤 원본을 orphan으로 바꾸면 상태도 끝내기도 `git` 오류이고
파일이 남는다. 오류를 0으로 보게 되돌리면 실패.

### [P1] 확인한 뒤 생긴 detached 커밋을 잃음

**검증**: 소스. 확인과 `git worktree remove` 사이에 세션이 살아 있었다. 탭을 닫는 것(세션 종료)은 삭제가 성공한 뒤였다.
`worktree remove`는 커밋하지 않은 변경만 막는다.

**수정**: 끝내기를 두 단계로 나눴다.
- `group_stop`:
  - 확인해서 끝낼 수 없는 상태면 세션을 건드리지 않고 멈춘다.
  - 아니면 ddak이 이 작업그룹 폴더에서 띄운 터미널을 모두 끝내고 기다린다 (`pty::stop_under`, 터미널마다 띄운 폴더를 실제
    경로로 기록).
  - 기존 `terminate`는 자식의 프로세스 그룹만 본다. 그런데 대화형 셸은 작업마다 그룹을 따로 만들어서, SIGHUP을 무시하는
    백그라운드 작업이 남았다 (실험: Rust 테스트에서 `terminate`로 바꾸면 계속 쓴다).
  - 그래서 세션(setsid, ID = 자식 PID) 전체에 SIGHUP과 SIGCONT를 보내고, 0.25초 뒤에도 남으면 SIGKILL을 보낸다. 좀비를 뺀
    구성원이 없어질 때까지(최대 3초) 기다린다. 다 끝나지 않으면 `running`으로 멈춘다.
- `group_end`: 그 폴더에 ddak 터미널이 다시 떴으면 `running`으로 멈춘다. 아니면 처음부터 다시 확인하고 지운다.
- 프론트:
  - 끝내는 동안 그 폴더의 탭은 터미널이 끝나도 창을 닫지 않는다.
  - 성공하면 그 폴더의 탭을 모두 닫는다.
  - 세션을 끝낸 뒤 실패하면 그 탭들의 터미널을 새 key로 다시 띄운다 (세션은 이어서 하기). 실패 문구와 함께 "다시 띄움"을
    알린다. 탭이 남으므로 고친 뒤 다시 끝내기를 누를 수 있다.

**남는 한계 (스펙에 적음)**: ddak 밖에서 띄운 프로세스와 세션을 떠난 프로세스(스스로 setsid한 데몬 등)는 막지 못한다.

**확인**
- Rust `stop_under_ends_whole_session_before_returning`:
  - `set -m`으로 그룹을 따로 만들고 SIGHUP을 무시하는 작업이, 돌아온 뒤에는 쓰지 않는다.
  - 다른 폴더의 터미널은 그대로다.
  - 세션 전체 대신 `terminate`로 되돌리면 실패.
- 자체 테스트 (`main`), 셸이 SIGHUP을 받으면 worktree에 파일을 만들게 해 둔 경우:
  - 끝내기가 "커밋하지 않은 변경이 생김"으로 멈춘다.
  - 탭이 남고, 다시 띄운 터미널이 명령을 받는다.
- 자체 테스트 (`main`), 3초 뒤 표시를 남기는 SIGHUP 무시 백그라운드 작업이 있는 경우: 끝낸 뒤 표시가 생기지 않는다.
- 수정 끄기:
  - 세션 끝내기 단계를 빼면 (이전 동작) 첫 검사가 실패한다 (끝내기가 그대로 성공해 대기 시간 초과).
  - 세션 전체 대신 그룹만 끝내면 둘째 검사가 실패한다 (`late-there`).

### [P2] 브랜치 삭제가 원본 HEAD 기준을 벗어남

**검증**: 실험. upstream이 있는 브랜치를 upstream에만 있는 새 커밋으로 옮기면 `git branch -d`가 지웠다.
- 경고: `deleting branch 'b' that has been merged to 'refs/remotes/origin/b', but not yet merged to HEAD`
- 종료 코드 0

git 문서와도 맞다 (upstream이 있으면 upstream 기준). 앞 리뷰의 3번 수정(`git branch -d`)은 체크아웃 보호는 맞았지만 이 기준이
달랐다.

**수정**: 지울 때 브랜치의 지금 커밋을 읽고, 다음을 모두 만족할 때만 `update-ref -d refs/heads/<브랜치> <그 커밋>`(기대값)으로
지운다.
- 그 커밋이 원본 HEAD에 있다.
- 브랜치를 쓰는 곳이 없다 (`branch_in_use`). git의 `branch_checked_out`(branch.c)과 같은 것을 직접 본다.
  - 각 worktree(원본 포함)의 `HEAD`
  - `rebase-merge`·`rebase-apply`의 `head-name`
  - `rebase-merge/update-refs`
  - `BISECT_START` (짧은 이름. 실험으로 확인)

브랜치가 그새 움직였으면 지우지 않고 "끝내는 중에 바뀜"으로 알린다. 검사와 지우기 사이에 누가 그 브랜치를 체크아웃하면, 그
worktree는 없는 브랜치에 남는다. 그래도 지운 커밋은 원본 HEAD에 있다 (스펙에 적음).

**확인**
- Rust `end_keeps_branch_moved_after_check`: 지우는 명령 직전에 브랜치와 upstream(같은 저장소의 브랜치)을 새 커밋으로 옮기는
  git 래퍼를 쓴다. 브랜치가 `changed`로 남고 새 커밋을 가리킨다. `git branch -d`로 되돌리면 실패.
- Rust `end_keeps_branch_being_rebased`: 원본에서 그 브랜치를 rebase하다 멈추면 (HEAD detached) `inUse`로 남는다.
  `end_keeps_branch_checked_out_elsewhere`와 함께, 쓰는 곳 검사를 끄면 둘 다 실패.

## 후속 리뷰 2: P1 두 건, P2 한 건 — 모두 타당, 수정

세션을 먼저 끝내는 방향과, 실패하면 다시 띄우는 동작에는 리뷰어가 동의했다. 확인 창 문구 제안도 받아들였다.

### [P1] 끝내는 중 새 터미널을 막지 않음

**검증**: 소스. 실행 중인 터미널 확인은 `group_end` 처음에 한 번뿐이었다. `pty_spawn`에는 아무 확인이 없어서, 그 뒤에 같은
폴더에 터미널을 띄우고 등록할 수 있었다.

**수정**
- `group_stop`과 `group_end`를 `group_end` 하나로 합쳤다. 순서: 확인 → 이 폴더를 잠금 (`pty::hold`, 함수가 끝날 때 풀림) →
  세션 끝내기 → 다시 확인 → 지우기.
- 잠근 동안 `pty_spawn`은 그 폴더와 그 안에 띄우지 않는다.
- 띄우기는 잠금 목록을 읽기로 잡은 채 확인·띄우기·등록을 한다. 잠그기는 쓰기로 잡는다. 그래서 띄우는 중이던 것은 등록을
  마친 뒤에 잠기고, 끝내기가 그것도 찾는다.
- 오류에 `stopped`(세션을 끝낸 뒤인지)를 담아, 프론트가 다시 띄울지 정한다.

**확인**: Rust `ending_folder_refuses_new_terminals`. 잠그면 그 폴더와 하위 폴더에는 띄우지 못하고, 다른 폴더는 띄운다. 풀면
다시 띄운다. 확인을 끄면 실패.

### [P1] 먼저 닫은 터미널의 백그라운드 작업을 놓침

**검증**: 소스. 일반 `pty_kill`은 목록에서 바로 빼고 프로세스 그룹만 끝냈다. 그래서 `stop_under`가 찾지 못했다.

**판단**: 일반 닫기도 세션 전체를 끝내게 했다 (리뷰어 안). 그러면 nohup으로 띄운 작업도 ddak 터미널을 닫으면 끝난다. 일반
터미널 앱은 SIGHUP만 보내서 nohup 작업이 남는 것과 다르다. 그래도 ddak 터미널을 닫으면 거기서 띄운 것이 끝나는 쪽이 이
도구에 맞다고 봤다 (지울 worktree에 계속 쓰는 프로세스가 남지 않게). 스펙에 적었다.

**수정**
- `terminate`가 세션 전체를 끝내는 하나뿐인 방식이다 (이전 `end_session`).
- 3초 안에 다 끝나지 않으면 자식을 거두지 않고 false를 돌려준다. 좀비 자식이 세션 ID를 쥐고 있어서 다시 불러도 안전하다.
- 닫기(`close`)는 두 목록을 함께 잡은 채 터미널을 "닫는 중"으로 옮긴다 (빠지는 틈이 없다). 다 끝나야 목록에서 뺀다.
- `stop_under`는 그 폴더의 열린 터미널과 닫는 중인 터미널을 모두 끝내고 기다린다.

**확인**: Rust `stop_under_waits_for_terminals_already_closed`.
- 닫기만 해도 SIGHUP 무시 작업(`set -m`)이 끝난다.
- 닫은 직후 끝내기는 그것까지 끝난 뒤에 돌아온다.
- 닫는 중 추적을 끄면 실패.
- 세션 대신 그룹에만 신호를 보내면 이 테스트와 `stop_under_ends_whole_session_before_returning`이 실패.

### [P2] 브랜치 사용 여부를 읽지 못하면 "안 씀"으로 봄

**검증**: 소스. `branch_in_use`가 읽기 오류를 빈 내용으로 바꿨다.

**수정**: 파일이 없으면 그 상태가 아닌 것으로 본다. 그 밖의 읽기 오류(권한 등)와 worktree 목록 오류는 오류다. 끝내기는 그
브랜치를 "쓰는지 확인하지 못함"(`unchecked`)으로 남긴다.

**확인**: Rust `end_keeps_branch_it_cannot_check`. 다른 worktree가 체크아웃한 브랜치에서 그 HEAD 파일을 읽지 못하게 하면,
`unchecked`로 남고 그 worktree는 그대로다. 읽기 오류를 빈 내용으로 되돌리면 실패.
