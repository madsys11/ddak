# 모바일 연결 1단계 리뷰 대응

대상: 브랜치 `ddak/mobile`, 기준 0bee299 + 커밋 안 한 작업 트리 (`src-tauri/src/mobile.rs`, `src/MobileDialog.tsx`, `src/mobile/*` 등).
설계: `docs/mobile-plan.md` "단계"의 1단계. 현재 동작: `docs/spec.md` "모바일 연결".

## 1차 리뷰 (채팅 #135)

| ID | 심각도 | 판단 | 근거 | 수정 | 확인 |
|---|---|---|---|---|---|
| R1 | P2 | 타당 | `forget`은 기기만 지우고, 스트림에는 기기 표시가 없어 `publish`가 모든 스트림에 계속 보냈다. 인증과 스트림 등록 사이에 끊으면 그 뒤에 등록될 수도 있었다. | 스트림을 (기기 id, 보낼 곳)으로 두고 `forget`이 같은 잠금 안에서 그 기기의 스트림을 뺀다 (보낼 곳이 사라지면 끝 조각을 쓰고 닫힘). 등록할 때 같은 잠금 안에서 기기가 아직 있는지 보고, 없으면 401. | Rust `forgetting_a_device_closes_its_stream`: SSE를 연 채 끊고 이벤트 → 스트림이 끝 조각으로 닫히고 이벤트 없음. 스트림을 빼는 줄을 끄면 실패. |
| R2 | P2 | 타당 | `more`는 `replace` 조회에서만 정했고, 겹친 조회는 마지막 것만 써서 처음 조회(`replace`)가 버려지면 `more`를 잃었다. | 채팅 상태를 `src/mobile/sync.ts` `MessageView`로 옮김. 최신 조회는 모두 통째로 바꾸며 `more`도 정한다. 겹치면 마지막 요청만 쓴다. | 자체 테스트 `mobileSyncUnit`: 두 조회가 어느 순서로 와도 11~60, more=true. |
| R3 | P2 | 타당 | 다시 이어질 때 최신 50개를 합치기만 해서, 끊긴 동안 50개 넘게 생기면 가운데가 빠지고 지운 대화가 남았다 (SSE 재생 없음, 놓친 `cleared`). | 처음·다시 이어짐·`cleared` 때 최신 페이지로 통째로 바꾼다 (더 읽어 둔 이전 페이지는 버림). 조회를 보낸 뒤 이벤트로 온 메시지는 남긴다. 이전 페이지 응답은 그 사이 바꾼 적이 없을 때만 붙인다. | `mobileSyncUnit`: 1~10 → 끊긴 동안 11~70 → 21~70+이전 버튼 → 이전 읽으면 1~70 연속. 지운 뒤 11만 남으면 11만. 조회 중 온 61 유지. 늦은 이전 페이지 버림. 합치기로 되돌리면 3건 실패. |
| R4 | P2 | 타당 | `pair`·`forget`이 잠금 안에서 사본을 만들고 잠금 밖에서 저장해, 늦은 저장이 끊은 기기를 되살릴 수 있었다. 같은 `.json.tmp`를 동시에 쓸 수도 있었다. | 설정·기기 목록은 상태 잠금을 쥔 채 저장 (`save_config`·`save_devices`가 잠금 안의 상태를 받음). 바꾼 순서 = 쓴 순서, 임시 파일 동시 쓰기 없음. | Rust `forgotten_device_stays_forgotten_after_restart`: 끊은 뒤 같은 폴더로 다시 만들면 A 거절, B 허용. (교차 순서 자체는 잠금으로 막았고, 테스트는 저장 결과를 본다.) |
| R5 | P3 | 일부 타당 | 큐가 무제한이라 받지 못하는 연결에 이벤트가 쌓일 수 있다. 쓰기 기한은 `into_writer`가 소켓을 감싸 이 코드에서 정할 수 없다. | 연결마다 `sync_channel(64)`, `try_send`가 실패(가득 참·닫힘)하면 그 연결을 뺀다 (폰은 다시 이어 다시 읽음). 쓰기 기한은 넣지 않음: 막힌 쓰기는 그 연결의 스레드만 붙잡고, 큐를 빼면 더 쌓이지 않는다. | Rust `stalled_stream_is_dropped`. |

질문 (API 버전): 이번 단계에서 강제한다. 프로젝트 목록은 버전이 다르면 목록을 비우고 안내만, 채팅도 열 때 `/api/info`를 보고
다르면 메시지·입력 없이 안내만 보인다.

## 재리뷰 1회째 (채팅 #137)

R1·R2·R4 해결, R5는 쓰기 기한 한계를 P3 비차단으로 남김. R3에 수정 경로의 차단 문제 하나:

| ID | 심각도 | 판단 | 근거 | 수정 | 확인 |
|---|---|---|---|---|---|
| R3 | P2 | 타당 | `older`·`earlier`가 최신 조회의 시작(`load`)만 비교해서, 최신 조회를 기다리는 동안 누른 이전 페이지가 새로 적용된 목록에 붙었다 (51~100 → 대기 중 이전 → 최신 151~200 → 이전 1~50 = 가운데 공백, more=false). 리뷰어 순서를 테스트로 돌려 재현됨. | 최신 조회를 기다리는 동안 `older`는 `before`를 주지 않는다 (화면이 요청하지 않음). 목록 세대(`gen`)를 최신 조회의 시작과 적용 때마다 올리고, `earlier`는 세대가 같을 때만 붙인다. | `mobileSyncUnit`에 그 순서 추가: before 없음, 늦은 응답 버림, 151~200 more=true. `before`만 막고 세대 비교가 `load`였을 때 이 검사가 실패함. |

## 재리뷰 2회째 (채팅 #139)

R1~R4 해결, R5 P3 비차단 유지. 새 범위로 차단 지적 하나. 재리뷰를 다 써서 사용자에게 올렸고(#140), 사용자가 R6을 고쳐 R6만
새로 리뷰받기로 정했다.

| ID | 심각도 | 판단 | 근거 | 수정 | 확인 |
|---|---|---|---|---|---|
| R6 | P2 | 타당 | 최신 조회가 실패하면 `MobileApp`의 실패 처리는 `setError`만 하고 `pending`을 그대로 둬서, 다음 최신 조회가 성공할 때까지 `older()`가 `before`를 주지 않았다 (이전 메시지 버튼이 요청을 보내지 않음). | `MessageView.fail(load)`: 마지막 조회의 실패일 때만 `pending`을 푼다. 목록은 그대로, 세대는 `begin`에서 이미 올라 그 전에 보낸 이전 페이지 응답은 붙지 않는다. `loadLatest` 실패 처리에서 부른다. | `mobileSyncUnit`: 51~100 → 조회 실패 → before=51. 조회 둘 중 앞의 것만 실패 → 아직 before 없음 → 뒤 응답 101~150 적용. `fail`을 비우면 첫 값이 undefined, 번호 비교를 빼면 둘째 값이 51이 되어 각각 실패함. |

## R6 별도 리뷰 (채팅 #144 → #145)

R6 해결, 새 차단 지적 없음. R1~R4 해결 유지, R5는 P3 비차단 한계(막힌 소켓 쓰기 기한)로 남긴다.
