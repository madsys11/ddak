# 파일 트리 git 표시 (2026-10-28)

사용자 요청: 파일 트리에서 수정·추가된 파일을 git처럼 표시. 무겁지 않으면 넣는다.

## 구현

- Rust (`git.rs`)
  - `git_place(dir)`: `git rev-parse --show-toplevel --show-prefix`로 폴더가 든 저장소의 최상위와 그 안 위치를 얻는다.
    저장소 밖이나 `.git` 안이면 None.
  - `git_status(repo)`: `git --no-optional-locks status --porcelain=v1 -z --untracked-files=normal`.
    표시는 M 수정, A 스테이징, U 추적 안 함, D 삭제, R 이름 바뀜, ! 충돌이다. 무시한 파일은 뺀다.
    이름 바뀜·복사는 다음 칸(원래 이름)을 건너뛴다.
- 프론트 (`gitStatus.ts`)
  - 저장소마다 한 번 읽어 펼친 폴더들이 함께 쓰고, 구독이 있는 동안 3초마다 다시 읽는다.
  - 폴더 감시 이벤트가 오면 바로 다시 읽는다.
  - 폴더 표시는 안의 것 중 가장 눈에 띌 것이다 (충돌 > 수정·삭제·이름 바뀜 > 추가·추적 안 함).
    추적 안 하는 폴더 안은 모두 U.
- 트리 (`FileTree.tsx`)
  - 이름 색과 오른쪽 끝 글자로 보인다. 폴더는 글자 대신 점이다.
  - 안에 든 저장소·worktree 행에는 바깥 저장소의 표시를 붙이지 않는다.
- 색
  - 새 토큰 `--git-modified`를 넣었다. 다크 #E2C08D, 라이트 #895503은 VS Code gitDecoration 값이고,
    Solarized는 대비 때문에 #7D5F00으로 진하게 했다.
  - 추가·추적 안 함은 `--git-added`, 충돌은 `--error`를 쓴다.
  - `statusContrastUnit`이 `--git-modified`도 본다.

## 판단

- **주기적으로 다시 읽는 이유:** 폴더 감시는 항목이 생기고 없어지는 것만 보고 하위 폴더는 제외한다. 그래서 내용 수정,
  `git add`, 커밋(`.git` 안만 바뀜)은 감시에 안 잡힌다. Git Graph처럼 3초마다 읽는다.
- **`--no-optional-locks`:** 몇 초마다 부르는 `git status`가 index를 고쳐 쓰면 `index.lock`을 잡는다.
  그러면 사용자가 터미널에서 돌리는 git 명령과 부딪친다. VS Code도 같은 이유로 이 옵션을 쓴다.
- **창이 숨어 있을 때도 읽는다:** 처음에는 숨으면 건너뛰게 했다. 그런데 화면이 잠긴 동안에는 커밋 뒤 표시가 남았고,
  돌아왔을 때도 3초 늦었다. 비용이 저장소마다 `git status` 한 번이라 건너뛰지 않기로 했다.

## 확인

- `cargo test` `git::tests::status_for_tree`
  - 수정, 충돌(병합), 추적 안 함 폴더 한 줄, 삭제, 이름 바뀜, 한글·공백 이름 스테이징, 무시 파일 제외를 본다.
  - `index.lock`이 남지 않는지, 하위 폴더 위치, `.git` 안과 저장소 밖이 None인지도 본다.
- 자체 테스트 `treeGit`
  - 새 저장소를 펼쳐 M·A·U·폴더 점, 저장소 행 자체에 표시가 없음, 추적 안 하는 폴더 안의 U를 확인한다.
  - 내용만 바꾼 파일의 M, 커밋 뒤 표시가 사라지는 것도 확인한다.
- 수정을 끄고 돌린 결과
  - 표시를 끄면(`git={undefined}`) 표시 검사 3개가 실패한다.
  - 주기적 다시 읽기를 끄면 "커밋하면 표시가 사라짐"이 실패한다.
    내용만 바꾼 파일은 감시 이벤트로도 잡혀서 그 검사는 통과했다.
- 전체 자체 테스트
  - `treeGit`, 대비 검사, restart·corrupt 등 다른 시나리오는 통과했다.
  - main 시나리오는 Mac 화면이 잠긴 상태(`CGSSessionScreenIsLocked`)라 창이 숨고 포커스가 없다.
    그래서 트리 화살표, 폰 채팅 스크롤, 배율, WebGL이 실패했다.
  - 이 밖에 돌릴 때마다 다른 검사 하나둘이 실패했다. 1회차는 프로젝트 제거 후 터미널 닫힘, 2회차는 검색 막대 포커스와
    채팅 깨우기였다. 프로젝트 단계는 혼자 두 번 돌려 둘 다 통과했다.
  - 화면 잠금이 풀린 뒤 다시 돌려야 전체 통과로 볼 수 있다.

## 리뷰 1차 (리뷰어 #307): 차단 4, 비차단 1

### R1 [P2] 추적 안 하는 폴더 안의 무시한 파일에도 U — 타당, 수정

확인: `--untracked-files=normal`은 `fresh/` 한 줄만 준다. 펼친 `fresh`는 이름과 관계없이 모두 U로 돌려서
`debug.log`(무시)까지 U였다. 실험 저장소에서 `git status`는 `?? fresh/`만,
`git ls-files --others --exclude-standard -- fresh/`는 `fresh/a.txt`만 낸다.

수정:
- `git_status(repo, open)`이 펼친 폴더 위치들을 받는다. 그중 추적 안 하는 폴더 안의 것은 그 폴더 아래를
  `ls-files --others --exclude-standard`(`--literal-pathspecs`)로 더 읽는다. 펼친 추적 안 하는 폴더 하나에 한 번이다.
- "모두 U" 처리는 지웠다.

확인:
- `status_for_tree`: `fresh/deep/` 위치를 주면 `fresh/deep/debug.log`는 빠지고 `fresh/top.txt`, `fresh/deep/f`만 더해진다.
  추가 읽기를 끄면 실패한다.
- 자체 테스트: 펼친 `fresh` 안의 `debug.log`는 표시가 없다. 위치를 넘기지 않으면 실패한다.

### R2 [P2] 펼쳐 둔 폴더에서 git init 하면 표시가 생기지 않음 — 타당, 수정

확인: `git_place`는 폴더가 바뀔 때만 불렀고, 폴더 감시 이벤트는 이미 아는 저장소만 다시 읽었다.

수정:
- 펼친 폴더마다 등록해 둔다. `refreshGitStatus(dir)`은 이벤트가 온 폴더와 그 아래 펼친 폴더만 저장소 위치를 다시 찾는다.
- 같은 저장소면 다시 읽기만 한다. 바뀌었으면 새 구독을 먼저 걸고 이전 구독을 푼다 (목록을 버렸다 다시 읽지 않게).

확인: 자체 테스트에서 저장소가 아닌 `gnew`를 펼쳐 둔 채 `git init` 하면 `one.txt`가 U가 된다.
다시 찾기를 끄면 실패한다.

### R3 [P2] 맥의 NFD 이름과 git의 NFC 경로가 안 맞음 — 타당, 수정

확인: 분해형 "한"으로 폴더를 만들면 `git status`와 `rev-parse --show-prefix`는 합성형(3바이트)으로 낸다
(`core.precomposeUnicode=true`). 트리 이름은 파일 시스템 그대로(분해형)다.

수정: `gitDecorations`가 맥에서는 git 경로, 위치, 항목 이름을 모두 NFC로 맞춰 비교한다. Windows는 그대로다.

확인:
- 자체 테스트가 분해형 한글 폴더(추적, 수정)와 파일(추적 안 함)을 실제로 만들어 M•, U와 폴더 안의 M을 확인한다.
- 순수 함수 검사: 맥은 NFC 경로와 NFD 이름, NFD 위치를 맞추고, Windows는 NFD 이름을 NFC 경로와 합치지 않는다.
- 맞추기를 끄면 두 검사가 실패한다. 폴더 안 검사는 위치도 git이 주는 NFC라 통과하고, NFD 위치는 순수 함수 검사가 본다.

### R4 [P2] 작업 트리 쪽 이름 바뀜(Y가 R·C)의 원래 이름 칸 — 타당, 수정

확인: `git add -N new.txt` 뒤 이름을 바꾸면 실제로 ` R new.txt\0old.txt\0`이 나온다. 전에는 `old.txt`를 상태 줄로 읽어
조회 전체가 실패했다.

수정: X나 Y가 R·C면 다음 칸을 건너뛴다. Y의 R은 R, Y의 C는 A로 본다. 파서를 `parse_status`로 나눴다.

확인: `status_worktree_rename`이 ` R`, ` C`, `RM`과 뒤따르는 정상 줄, 잘못된 줄의 오류를 본다. Y 처리를 끄면 실패한다.

### R5 [P3] 폴더 이벤트 하나가 관계없는 저장소까지 다시 읽음 — 타당, 수정

R2와 같은 수정이다. 이벤트가 온 폴더와 그 아래 펼친 폴더의 저장소만 다시 읽는다.

측정:
- 이 저장소(추적 파일 176개)에서 `git --no-optional-locks status --porcelain=v1 -z`는 5번에 0.063초, 한 번에 약 13ms다.
- 호출 수: 펼친 폴더가 있는 저장소마다 3초에 `git status` 한 번이다. 펼친 추적 안 하는 폴더가 있으면 그 폴더마다
  `ls-files` 한 번을 더한다. 폴더 감시 이벤트마다 그 아래 펼친 폴더 수만큼 `rev-parse`를 부른다.
- 범위: 13ms는 이 저장소 하나의 `git status` 측정이다. 모든 저장소에서 같은 비용이라는 근거는 아니다.
  `ls-files`는 `git status`가 묶어 준 추적 안 하는 상위 폴더 전체를 읽는다. 그래서 펼치지 않은 하위 폴더의 파일 수에
  따라서도 비용이 는다.
