# 깨우기 미루기와 claude 폴더 신뢰 (2026-10-25)

**요청**: orca 비교 보고서의 1~3번 진행 — OSC 7501 상태 수신, claude 폴더 신뢰 미리 기록, 깨우기 전 선택 창 검사.
목적은 같다: 깨우기의 Enter가 열린 선택 창(권한 확인, 폴더 신뢰)의 답을 고르지 않게 한다 (spec "다음 단계" 1번의 한계).

## 실험 (python pty, 2026-10-25)

- claude 2.1.310: 시작 0.3초에 `ESC]7501;?`, 바로 뒤 DA1(`CSI c`). 답하면 `state=idle:app=claude-code`.
  짧은 질문: working → done. `--settings '{"permissions":{"ask":["Bash"]}}'`로 권한 확인을 띄우면
  `state=blocked:kind=permission:msg=<base64 "approve Bash: echo ddak-probe">`가 약 2.7초에 왔다 (기존 permission_prompt
  훅은 약 6초 뒤).
- claude 폴더 신뢰 창(신뢰하지 않은 폴더)은 물음만 보내고 상태를 보내지 않았다. 화면: "❯ … No, exit / Yes, I trust this
  folder / Enter to confirm · Esc to cancel". → 3번(화면 검사)과 2번(미리 기록)이 필요하다.
- claude는 git worktree 하위 폴더를 상위 폴더 신뢰로 보지 않았다 (`dev-review-9`는 신뢰, 그 안의 `ddak`은 물음).
- codex 0.164: 묻지 않아도 `state=idle|working:app=codex`.
- codex의 신뢰: 이 사용자 설정은 홈 폴더(`~`)를 신뢰해 ~/.ddak 아래에서 묻지 않았다. 새 폴더에서의 동작은 확인하지
  못했다 (codex가 터미널 응답을 더 기다려 화면이 나오지 않음). codex 신뢰는 적지 않고 화면 검사에 맡긴다.

## 구현

- `src/programStatus.ts`: OSC 7501 본문 해석(orca protocol.ts를 줄임: 상태·blocked의 종류·msg base64, 하위 기록 무시,
  clear), 물음의 답, 화면 선택 창 판단(orca claude-open-dialog-hold.ts + codex의 "Press enter to confirm or esc to
  cancel"과 `›`), 기다림 = blocked 또는 10분 안의 선택 창.
- `Terminal.tsx`: `registerOscHandler(7501)` — 물음에는 `sending` 줄에 `pty_write(user: false)`로 답한다 (PTY가 아직 없으면
  생길 때까지 기다린다). xterm이 같은 해석 중에 DA1 응답을 onData로 내기 전에 줄에 들어가 순서가 맞다. `onWriteParsed`
  뒤 0.1초에 화면 아래 14줄 검사. 기다림이 바뀌면 `pty_awaiting`, 상태·기다림이 바뀌면 onStatus.
- `pty.rs`: Session.awaiting. wake_tick은 바로 깨우기가 아니면 awaiting 동안 넘어가고, Enter 전에도 본다.
- `Workspace.tsx` StatusBadge: 이름표에 상태.
- `claude_trust.rs`: group_create에서 원본 프로젝트가 신뢰면 작업그룹 폴더를 적는다. claude의 잠금(proper-lockfile:
  `<파일>.lock` 폴더)을 잡고, 잠금 안에서 다시 읽어 적고, 같은 권한의 임시 파일 → rename. 링크면 가리키는 파일.
  serde_json `preserve_order`로 사용자 파일의 키 순서를 지킨다 (앱 전체에 켜짐. cargo test 전부 통과).

## 리뷰 1차 (#102)

**R1 [P2] 링크인 설정 파일의 잠금 대상과 쓰기 대상이 다름 — 타당 (부분).** 리뷰는 proper-lockfile 기본(realpath: true)으로
claude가 실제 경로를 잠근다고 보고, orca(claude-folder-trust-file.ts)는 "claude는 링크여도 적힌 경로를 잠근다"며
realpath: false로 잠근다. 어느 쪽인지 claude 소스로 확인하지 못했으므로 둘 다 잠근다. 수정: 잠금 전에 실제 경로를 정하고,
링크면 링크 경로와 실제 경로의 `.lock`을 모두 잡는다 (하나라도 못 잡으면 잡은 것을 풀고 Locked). 잠금 안의 읽기·바꾸기는
실제 파일. 확인: leaves_config_alone_when_unsure — 실제 파일의 잠금이 있으면 Locked, 파일 그대로, 링크 쪽 잠금은 풀림.
실제 경로 잠금을 빼면 실패한다.

**R2 [P2] 바로 깨우기가 기다리는 프로그램에 Enter를 보내지 않음 — 타당.** 뒤 스레드가 force를 몰랐다.
**R3 [P2] Enter 전에 기다리게 되면 알림이 사라짐 — 타당.** 대기 항목은 지웠고 Enter는 다시 보내지 않았다.
수정 (둘 다): Enter를 스레드 대신 세션의 `enter` 상태로 둔다 ({at, before, force, deferred}). wake_tick이 먼저 Enter 차례를
본다:
- 사용자가 친 키가 기준보다 뒤면 그만둔다 (초안). 기준: 미루지 않았으면 알림을 쓸 때의 입력, 미뤘으면 그것과 기다림이 마지막으로
  바뀐 때(`awaiting_changed`) 중 늦은 것. 그래서 선택 창에 답한 키는 초안이 아니다.
- 기다리는 중이고 바로 깨우기가 아니면 미룬다.
- WAKE_GAP이 지났으면 Enter.
Enter를 기다리는 창에는 다음 알림을 쓰지 않는다. Enter는 300ms 넘게 지난 다음 확인(0.25초마다)에서 간다.
확인: wake_holds_while_program_awaits_user — 기다리는 동안 알림·Enter 없음, 선택 창에 답한 키("1") 뒤 기다림이 끝나면 Enter 한 번,
끝난 뒤 친 키("x")는 초안이라 Enter 없음, 바로 깨우기는 기다려도 알림과 Enter. force를 빼면 바로 깨우기 검사가, 기준에서
awaiting_changed를 빼면 선택 창 답 검사가 실패한다. 기존 wake_writes_notice_then_enter_when_quiet는 Enter를 확인으로 보내게
기다림에서 wake_tick을 돌리도록 고쳤다.

**R4 [P2] 문서에 실제 홈 경로 — 타당.** "홈 폴더(`~`)"로 바꿨다.

## 리뷰 2차 (#104)

**R3 [P2] 선택 창에 답하는 키가 아직 초안으로 처리됨 — 타당.** (1) 기다리는 중 친 키 뒤 다음 확인에서, 초안 검사가 "기다리면
미룸"보다 먼저라 취소됐다. (2) 확인 사이에 기다림이 시작되고 끝나면 deferred가 서지 않아 기준이 알림 때 입력이었다.
수정: 기다리는 동안(force 아님)은 무엇을 쳐도 Enter를 그대로 둔다 (초안 검사보다 먼저). "알림 뒤에 기다린 적이 있는지"는
확인이 본 것 대신 기다림 변경 횟수(`awaiting_changes`, set_awaiting에서 늘림)로 안다: Enter에 그때 횟수를 적고, 달라졌으면
기준은 max(알림 때 입력, 마지막 변경 때 = 기다림이 끝난 때).
확인: wake_holds_while_program_awaits_user에 (1) 답 키 뒤에도 기다리는 채 확인을 돌려 Enter 없음 → 끝나면 Enter 한 번,
(2) 확인 없이 기다림 시작·답 키·끝 → Enter 한 번을 더했다. 끝난 뒤 친 초안은 계속 취소된다. 순서를 되돌리면 (1)이, 횟수 기준을
빼면 (1)부터 실패한다 ((2)만 따로 실패하는지는 이 실험으로 가르지 못했다).
