## 1. 터미널 자동 응답을 사용자 입력으로 기록함 — 타당, 수정

**검증**: 소스. xterm의 `onData`에는 키 입력뿐 아니라 프로그램 질의에 대한 자동 응답(커서 위치 `ESC[행;열R`, 포커스, 장치
속성 등)도 온다. 그런데 `pty_write`가 모두 입력 상태에 넣었다. 커서 위치 응답 하나로 "초안 있음"이 되어 깨우지 않았다.

**수정**
- `pty_write`에 `user`를 둔다. 사용자 입력일 때만 입력 상태에 넣고, 데이터는 늘 보낸다.
- 프론트(`Terminal.tsx`)는 다음 둘을 모두 만족할 때 사용자 입력으로 본다.
  - 키·붙여넣기·IME 이벤트(keydown, keypress, beforeinput, input, paste, composition*) 뒤 300ms 안에 나온 데이터다.
    IME 조합 결과는 xterm이 setTimeout으로 조금 뒤에 보내서 시간 창을 둔다.
  - 터미널 자동 응답 모양(CPR, 포커스, DA, DECRQM, OSC, DCS)이 아니다 (`isTerminalReply`). 키 바로 뒤에 프로그램이 질의해서
    온 응답도 빼려고 모양도 본다.
- 프로그램이 쓴 입력(`term.input`)은 사용자 입력이 아니다.

**확인**
- Rust `wake_writes_notice_then_enter_when_quiet`: 사용자 입력이 아닌 커서 위치 응답은 초안 상태를 바꾸지 않고 깨우기를 막지
  않는다. 구분을 끄면 실패.
- 자체 테스트:
  - 응답 모양 판별 단위 검사 (응답 9개는 응답, 키·붙여넣기 11개는 아님).
  - listener가 시작할 때 커서 위치를 물어 xterm이 실제로 응답하게 한 뒤에도, 한 번도 치지 않은 창으로 보고 바로 깨운다.
    사용자 입력 판별을 끄면(모두 사용자로) 실패.
  - 초안은 실제 키 이벤트로 친다 (`typeKeys`). 처음에는 keydown과 keypress가 둘 다 글자를 보내 두 번 들어갔다. keydown으로
    나오지 않을 때만 keypress를 보내게 고쳤다.

## 2. 리스너 등록 전에 온 깨우기 상태를 놓침 — 타당, 수정

**수정**: 터미널은 `chat-wake` 등록이 끝난 뒤에 띄운다. 등록에 실패해도 띄운다 (배지만 못 본다). 참여(토큰)는 띄울 때
생기므로, 등록 전에는 대기 상태가 생기지 않는다. 생성 응답(id)보다 먼저 온 이벤트는 이전처럼 모아 둔다.

**확인**: 자체 테스트. 개발 빌드 훅 `wakeListenDelay`로 등록을 1.5초 늦추면, 터미널이 1.5초 넘게 지나서 뜬다 (1.6초). 등록을
기다리지 않게 되돌리면 실패.

## 3. 이전 깨우기의 해제 이벤트가 새 대기 배지를 지움 — 타당, 수정

**수정**: 대기 상태가 바뀔 때마다 `wakes` 잠금 안에서 전역 변경 번호(`wake_seq`)를 매겨 이벤트에 싣는다
(`{ pty, pending, seq }`). 터미널은 이미 본 것보다 오래된 번호를 버린다.

**확인**
- Rust: 깨운 뒤의 번호가 대기 때의 번호보다 크다.
- 자체 테스트: 대기(번호 N)를 보낸 뒤 오래된 해제(N-1)를 보내도 배지가 남고, 새 해제(N+1)에 사라진다. 번호 검사를 끄면 실패.

## 후속 리뷰: 자동 응답 일부를 놓침 — 타당, 수정

**검증**: 소스. 판별식이 `CSI 0 n`(상태 질의 응답)과 `CSI ? 행;열 R`(DEC 커서 위치)을 놓쳤다. 설치된 xterm 6.0.0 소스에서 자동
응답을 만드는 곳(`triggerDataEvent`)을 모두 찾았다 (InputHandler, CoreBrowserTerminal).
- 장치 속성: `CSI ? 1;2 c`, `CSI ? 6 c`, `CSI > … c` (`linux` 터미널 이름의 `<n>c`는 쓰지 않는다)
- 모드 질의: `CSI ? m;v $ y`
- 상태: `CSI 0 n`
- 커서 위치: `CSI 행;열 R`, `CSI ? 행;열 R`
- 창 정보: `CSI 8|4|6 ; … ; … t`
- DCS(`ESC P … ESC \`), OSC 색 응답, 포커스(`CSI I`·`CSI O`)

**수정**: 하나씩 더하지 않고 일반 규칙으로 바꿨다. `CSI [?>]? [숫자;]* (c|n|R|t)`, `CSI ?? [숫자;]* $y`, DCS, OSC, 포커스다.
- xterm 키보드(Keyboard.ts)가 만드는 CSI는 `~`, `A`–`D`, `H`, `F`, `P`–`S`, `Z`로 끝나서 `c`·`n`·`t`·`$y`와 겹치지 않는다.
- `R`로 끝나는 키는 수식키+F3(`CSI 1;n R`, Keyboard.ts 238행)이다. 커서 위치 응답과 모양이 같지만 글자를 쓰는 키가 아니라
  응답으로 봐도 초안 판단에는 상관없다.

**확인**
- 단위 검사: 위 응답 18개는 응답이고, 키·붙여넣기 18개(화살표, 수식 화살표, Home/End, F1, 수식 F1, F5, 수식 F12, ⇧Tab,
  DEL, ^C, 한글, 붙여넣기 등)는 응답이 아니다. 예전 판별식으로 되돌리면 응답 다섯 개를 놓쳐 실패.
- 자체 테스트: listener가 줄을 받을 때마다 `ESC[5n`과 `ESC[?6n`을 묻는다. 사용자가 실제 키로 "hi"와 Enter를 친 직후 xterm이
  응답해도, 다음 멘션은 조용해지면 누르지 않아도 깨운다. 예전 판별식이면 실패.
- Rust: 알림과 Enter 사이에 온 자동 응답(사용자 입력 아님)은 Enter를 막지 않는다. 같은 테스트에서, 입력 구분을 끄면 앞쪽
  단언에서 먼저 실패한다.
