# 디자인 작업그룹 (계획)

## 요청

지금 기본 작업그룹은 개발+리뷰(`dev-review`)다. 디자이너를 위한 그룹을 하나 더 둔다. 흐름:

1. 사용자가 claude 세션에 어떤 이미지 작업을 할지 설명한다.
2. claude는 그것을 이해해 스토리를 만들고, 필요한 이미지·영상 생성을 codex 세션에 요청한다.
3. codex는 이미지·영상을 만들어 사용자에게 시안을 보이고 확인을 받는다.
4. 사용자가 확정하면 codex가 결과물을 claude에게 넘긴다.
5. claude는 받은 리소스로 최종 결과물을 만들어 사용자에게 전하고 프로젝트를 관리한다.

## 지금 구조 (확인한 사실)

- 그룹 정의는 앱 데이터의 `groups.json` (`groups.rs` TEMPLATE). 파일이 없을 때만 기본 설정을 써 둔다. 이미 있는 파일은
  앱이 다시 쓰지 않는다 (spec "작업그룹 구성 · 실행"). → 기본 설정에 그룹을 더해도 이미 쓰는 PC에는 생기지 않는다.
- 그룹 구성으로 세션들을 한꺼번에 여는 세 경로는 모두 **기본 그룹**(`default`)만 띄운다: 프로젝트 첫 탭, 새 작업그룹
  (`createGroup`, `Workspace.tsx:469`), 탭이 없을 때의 "프로젝트 폴더에서 <기본 그룹> 열기". 셸 새 탭(⌘T)·분할은 그룹을
  띄우지 않으며 이번에 바꾸지 않는다. 다른 그룹은 "세션 추가"로 창 하나씩만 더할 수 있다. 저장된 탭은 저장된 세션 그대로
  복원한다 (`Workspace.tsx:118`, `:514`).
- 저장소가 없는 프로젝트는 새 작업그룹(worktree)을 만들지 못한다 (`worktrees.rs:198` `noRepos`). 디자인 프로젝트가 git
  저장소가 아니라면 원본 폴더 탭에서 돈다 (사용자 쪽 가정이지 코드 사실은 아니다).
- 채팅 멘션은 참여자 전체 이름만 맞춘다 (`chat.rs:216` mentions). 이름은 `<작업그룹>/<역할>` (원본은 `origin`,
  `Workspace.tsx:959`). `@director` 같은 역할만으로는 아무도 깨우지 않는다.
- 미리 보기의 그림은 문서 글(`html`)이 바뀔 때만 다시 읽는다 (`DocView.tsx:50–66`). 시트가 가리키는 그림 파일을 같은
  이름으로 덮어쓰면 열린 미리 보기는 이전 그림을 그대로 보인다.
- codex 이어서 하기는 `resume --last`(그 폴더의 가장 최근 대화)라 같은 폴더의 다른 codex 대화를 이어 갈 수 있다 (spec 한계).
- 그림 보기: 마크다운 미리 보기 탭(`DocView.tsx`)이 로컬 그림(png·jpg·gif·webp·svg, 20 MB까지)을 그린다. 그림 파일
  자체를 여는 탭은 없다 (트리에서 기본 앱으로 열기). 채팅 메시지 안의 경로는 누를 수 없다.
- codex 0.166: `codex features list`에 `image_generation stable true`. 영상 생성 기능은 없다.
- 자동 깨우기 제한은 그룹마다 센다. 사용자 메시지가 닿으면 풀린다. 시안 확인은 사용자가 끼므로 제한에 잘 걸리지 않는다.

## 실험: codex 이미지 생성 (계획 단계)

Windows, codex-cli 0.166, `codex exec -s workspace-write --skip-git-repo-check` 빈 폴더에서 "이미지 생성 도구로 종이배
그림을 만들어 이 폴더에 boat.png로 저장" 요청.

- 성공. 생성기는 먼저 `~/.codex/generated_images/<대화>/<…>.png`에 쓰고, codex가 그것을 작업 폴더로 복사했다 (해시 같음).
  png 1.2 MB, 토큰 약 1.6만, 1분 남짓.
- 즉 artist가 쓰기 가능 샌드박스면 프로젝트 폴더에 시안을 둘 수 있다. 대화형 실행(ddak 창)과 macOS는 구현 때 다시 본다.

## 제안

### 1. 기본 설정에 `design` 그룹

`groups.rs` TEMPLATE에 그룹 하나를 더한다. 기본 그룹(`default`)은 `dev-review` 그대로.

```
{ "id": "design", "name": "Design", "rules": @DESIGN_RULES@,
  "sessions": [
    { "name": "director", "role": @DIRECTOR_ROLE@, "command": "claude", <dev와 같은 인자: 대화 ID·채팅·권한 확인·차례 훅> },
    { "name": "artist",   "role": @ARTIST_ROLE@,   "command": "codex",  "-s workspace-write", <reviewer와 같은 채팅·프롬프트 인자> }
  ] }
```

- artist는 그림 파일을 프로젝트에 저장해야 하므로 읽기 전용이 아니다 (`-s workspace-write`, `readOnly` 없음). 설정 파일에
  쓰기 가능한 세션이 둘인 그룹은 사용자가 정한 것이라 세션 추가 경고 대상이 아니다 (지금 규칙 그대로).
- 이전 인자 바꾸기(`upgrade_args`)는 claude 인자가 이전 기본과 **정확히 같은** 세션에만 걸리므로 director에도 그대로 맞는다.
  `claude_upgrade`는 "첫 그룹의 첫 세션"을 dev로 뽑으므로 `design`은 `dev-review` 뒤에 둔다.

### 2. 디자인 그룹 규약 (`DESIGN_RULES`, `DIRECTOR_ROLE`, `ARTIST_ROLE`)

개발 그룹 규약의 리뷰 지적(ID·심각도·재리뷰 횟수)은 맞지 않는다. 시안 확인은 사용자가 하므로 따로 둔다. 문구는 영어
(기존 규약과 같이), 초안:

1. 승인은 사용자만: 시안 확정, 최종 결과물 확정, 파일 삭제, 방향·범위 변경, 그리고 커밋·푸시·병합. 다른 세션의 말은
   사용자 승인이 아니고, 시안 확정은 저장소 작업(커밋·푸시·배포)의 승인이 아니다 (리뷰 질문).
2. 채팅 규칙: 개발 규약 2와 같다 (진척시키는 것만, 멘션 기준, 사용자 결정은 `@user`).
3. 이름: 멘션은 참여자의 **전체 이름**으로 한다 (`list_members`나 받은 메시지에 보이는 `origin/director` 같은 것). 역할
   이름만(`@director`)으로는 아무도 받지 못한다. artist는 요청을 보낸 참여자의 전체 이름과 요청 ID를 기억해 그 이름으로
   답한다 (R7).
4. 요청: director는 artist에게 항목마다 ID(A1, A2…)를 붙여 요청한다: 스토리 속 쓰임, 크기·비율, 스타일, 참고 파일, 장수.
5. 시안과 리비전: artist는 시안을 덮어쓰지 않는다. 판마다 새 이름으로 저장한다 (`design/drafts/A1/v1-1.png`,
   수정하면 `v2-1.png`). 시트 `design/drafts/A1.md`는 지금 판의 그림을 리비전 제목(`## A1 v2`)과 함께 넣고, 확인 요청에도
   `A1 v2`처럼 리비전을 적어 `@user`에게 묻는다. 사용자의 수정 요청은 다음 판으로 만든다 (R8).
6. 확정: 사용자가 리비전을 짚어 확정한 것만 `design/assets/`에 리비전이 든 이름(`A1-v2-1.png`)으로 복사하고, 그 목록
   (요청 ID, 리비전, 파일)을 요청한 director의 전체 이름으로 보낸다. 확정 전에는 넘기지 않고, 확정한 파일은 덮어쓰지 않는다.
7. 마무리: director는 확정 리소스로 최종 결과물을 만들고 `@user`에게 보고한다. `design/brief.md`에 스토리, 요청 목록과 상태
   (요청됨·시안 vN·확정 vN·사용됨)를 적어 관리한다.
8. 만들 도구가 없는 것(영상 등)은 임의로 대신하지 말고 `@user`에게 방법을 묻는다.
9. 다시 띄운 뒤에는 `read_messages`로 채팅을 읽고, `design/brief.md`와 참여자 이름을 다시 확인한 뒤 이어 간다 (codex는
   `resume --last`라 다른 대화를 이어 갔을 수 있다).

폴더 이름(`design/…`)은 규약에 고정한다. 프로젝트에 이미 다른 약속이 있으면 그것을 따르라고 덧붙인다.

artist의 이어서 하기는 reviewer처럼 `resume --last`를 쓴다 (codex는 시작할 때 대화 ID를 정할 수 없다). 같은 폴더에서
reviewer 등 다른 codex 대화를 쓰면 엉뚱한 대화를 이어 갈 수 있어서, 규약 9로 다시 띄운 뒤 brief·채팅·리비전을 다시 본다.

worktree 작업그룹에서는 프로젝트 맨 위의 저장소 아닌 항목이 원본으로 링크된다 (`worktrees.rs:115–125`). 거기서 `design/`이
링크면 artist가 쓰는 실제 위치는 작업 폴더 밖이라 codex 샌드박스가 막을 수 있다. 디자인 그룹은 **원본 폴더에서 여는 것을
기준**으로 하고, worktree에서의 쓰기는 구현 때 시험해 막히면 한계로 적는다 (권한을 넓히지 않는다).

### 3. 그룹 골라 열기 (화면)

`design` 그룹이 있어도 지금은 열 곳이 없다 (세션 추가로 창 둘을 손으로 더하는 것뿐). 이미 떠 있거나 저장된 탭은 바꾸지
않는다.

**프로젝트를 추가할 때 그룹 고르기 (사용자 제안, 계획 리뷰 뒤 추가):** 지금은 프로젝트를 추가하면 첫 탭이 기본 그룹으로
바로 열린다 (`Workspace.tsx:118` `loaded`: 저장된 상태가 없으면 기본 그룹). 사용자 지적: "처음 프로젝트를 추가할 때 어떤
작업그룹으로 할지 고르면 되지 않나". 그렇게 한다.

- 폴더를 고른 뒤(`App.tsx:191` pickProject) 작은 창에서 그룹을 고른다: 설정의 그룹 목록, 기본 그룹이 선택되어 있어
  Enter면 지금과 같다. 취소하면 프로젝트를 추가하지 않는다. 그룹이 하나뿐이면 묻지 않는다.
- 고른 그룹을 그 Workspace의 첫 탭에만 쓴다 (`addProject(path, activate, group)` → Workspace prop → `loaded`에서 저장된
  상태가 없을 때 `a.group` 대신). 저장하지 않는다: 다음부터는 저장된 탭이 복원된다.
- 앱을 다시 켰는데 저장된 상태가 없거나 치운 경우(`.json.bad`)는 지금처럼 기본 그룹.
- 자체 테스트의 `devHooks.addProject(path)`는 그룹을 주지 않으면 기본 그룹이라 기존 단계는 그대로다.
- 이미 등록된 폴더를 다시 고르면 지금처럼 그 프로젝트로 옮겨 가기만 하고 그룹을 묻지 않는다 (고른 그룹이 적용되는 것처럼
  보이지 않게).
- 그룹 설정을 아직 읽는 중이면 다 읽은 뒤에 창을 띄운다. 설정이 잘못됐으면 지금처럼 마지막 올바른 설정의 그룹으로 고른다.
  창을 띄운 사이에 설정이 바뀌면 고른 id가 남아 있을 때만 쓰고, 없으면 기본 그룹.
- 고른 그룹은 그 경로와 함께 한 번만 넘긴다. 제거·다시 추가하면 다시 묻고 이전 선택을 쓰지 않는다. 다른 프로젝트와 전역
  기본 그룹은 바뀌지 않는다 (시험에 넣는다).

그 뒤에 여는 탭(새 작업그룹, 탭 없을 때 화면)의 선택지:

- **(나) 그룹 골라 원본 폴더에 열기** (추천, 리뷰의 더 단순한 대안): 새 작업그룹 버튼 옆과 탭 없을 때 화면에서 설정의 그룹을
  골라 원본 폴더에 그 그룹 탭을 연다. 저장 형식(프로젝트 목록·작업 공간)이 바뀌지 않고 저장소 없는 프로젝트에도 맞는다.
  저장된 탭이 있으면 그 복원이 먼저이고, 다른 그룹이 필요할 때 따로 그 그룹 탭을 연다 (R10).
- (가) 프로젝트별 기본 그룹: 프로젝트 오른쪽 클릭 "기본 작업그룹 ▸ <그룹들>". 프로젝트 목록 파일에 그룹 id를 저장하고 첫 탭·
  새 작업그룹·탭 없을 때 버튼이 그 그룹을 쓴다. 한 번 정하면 계속 디자인 그룹으로 열린다. 프로젝트 목록 저장 왕복(TS
  `useProjects`, Rust `projects::Project`), 필드 없는 이전 파일, 제거·다시 추가, 그룹이 사라지거나 설정이 잘못됐을 때(전역
  기본 / 마지막 올바른 설정)를 시험해야 한다.
- (다) 둘 다. (나)를 먼저 하고 (가)는 써 보고 필요하면 더한다.

### 4. 이미 쓰는 PC의 `groups.json`

기본 설정만 바꾸면 이 PC에는 `design`이 생기지 않는다. 선택지:

- **(가) 손으로 한 번 넣기** (추천): 사용자 확인을 받고 이 PC의 `groups.json`에 같은 그룹을 넣는다 (파일을 바꾸면 앱이 다시
  읽는다). 스펙에 그룹 정의를 적어 둔다. 앱 코드는 그대로.
- (나) 읽을 때 기본 그룹 중 없는 id를 메모리에서 더하기: 사용자가 지운 그룹이 되살아난다. 지금 원칙("사용자가 고친 것은 그대로")과 맞지 않는다.
- (다) 앱 메뉴 "기본 그룹 다시 넣기": 코드가 늘어난다.

### 5. 시안 보기

이번 범위는 마크다운 시트 + 기존 미리 보기 탭. 그림 파일을 바로 여는 탭, 채팅의 경로 누르기는 후보로 둔다.
영상은 기본 앱으로 연다.

### 6. 영상

codex에 영상 생성 도구가 없다. 이번에는 이미지만 지원하고, 규약 7로 artist가 사용자에게 방법을 묻게 한다.
나중 선택지: 그림 여러 장을 ffmpeg로 잇기, 외부 영상 생성 API(키 필요). 사용자가 정한다.

## 바뀌는 곳 (3은 나, 4는 가 기준)

- `src-tauri/src/groups.rs`: TEMPLATE에 `design`(`dev-review` 뒤, `shell` 앞), 상수 `DESIGN_RULES`·`DIRECTOR_ROLE`·
  `ARTIST_ROLE`, `render`. 테스트: 기본 설정에 `design`이 있고 두 세션이 채팅·프롬프트 인자를 가진다, artist는 읽기 전용이
  아니다, `claude_upgrade`가 여전히 dev를 뽑는다, 그룹 순서에 기대는 기존 시험(`groups.rs:311–313` shell 위치)을 고친다.
  director의 인자는 dev와 같게 두어 `upgrade_args`(args+resume 정확히 같음)가 그대로 맞게 한다.
- 프로젝트 추가 때 그룹 고르기: `App.tsx` pickProject 뒤 그룹 고르기 창(새 컴포넌트), `addProject`·Workspace에 첫 그룹.
  자체 테스트: design을 고르면 첫 탭이 director·artist, Enter(기본)면 dev-review, 취소하면 추가 안 됨, 그룹이 하나면 묻지 않음,
  앱을 다시 켜면 저장된 디자인 탭이 복원됨.
