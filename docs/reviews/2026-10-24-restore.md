# 리뷰 대응: 상태 저장·복원 (2026-10-24)

리뷰 범위: `b787d7f` 이후 커밋 전 작업 트리 (`workspace.rs`, `workspaceState.ts`, `Workspace.tsx`, `pty.rs` fallback,
`groups.rs` resume). 지적 6건(P1 1, P2 5). 5건은 타당해서 리뷰어 안대로 고쳤다. codex 창별 복원 1건은 문제는 맞지만
방식이 달라 한계로 남긴다. 테스트마다 수정을 잠시 끄고 실패하는 것을 확인했다.

## 1. [P1] 읽기 실패 뒤 기존 상태를 덮어씀 — 타당, 수정

**검증**: 소스. 프론트는 읽기 오류를 "저장 없음"으로 보고 기본 상태를 자동 저장했다. Rust도 정상 JSON이 권한 오류로
읽히지 않으면 깨진 파일로 보고 `.bad`로 치웠다.

**수정**
- Rust `load`: 파일 없음 → None, 내용이 깨짐(UTF-8 아님 `InvalidData`, JSON 아님) → `.bad`로 치우고 None, 그 밖의 읽기
  실패 → 오류.
- 프론트: 읽기 오류면 기본으로 열되 사이드바에 알리고, 그 프로젝트는 앱을 다시 켤 때까지 저장하지 않는다
  (`saveBlocked`). JSON이지만 모양이 틀리면 `workspace_set_aside`로 치운 뒤 저장한다 (치우지 못하면 읽기 실패와 같이).

**확인**
- Rust `roundtrip_and_broken_file`: 권한 0000 파일 → 오류, 내용 그대로. UTF-8이 아닌 파일 → 치움.
  읽기 실패 구분을 끄면 실패.
- 자체 테스트 (`main`): 목록에서 뺐다가 다시 넣을 때 읽기 실패를 넣으면, 알림이 뜨고 탭을 바꿔도 저장된 파일의 해시가
  그대로다.

## 2. [P2] 저장 요청 순서가 보장되지 않음 — 타당, 수정

**검증**: 소스. invoke는 요청마다 따로 가서 도착 순서가 보장되지 않는다 (터미널 입력 전송과 같은 이유).

**수정**: Workspace마다 저장을 줄 세운다. 앞 저장이 끝난 뒤에 다음을 보낸다.

**확인**: 자체 테스트 (`resume-save`). 개발 빌드 전용 `devHooks.workspaceSaveDelay`로 첫 저장을 1.5초 늦추고, 그동안
탭을 열었다 닫는다. 파일은 마지막 상태(탭 하나)여야 한다.

## 3. [P2] 복원 중 새 작업그룹을 만들면 결과가 사라짐 — 타당, 수정

**수정**: 읽기 전이면 `createGroup`이 `group_create`를 부르기 전에 돌아온다.

**확인**: 자체 테스트 (`main`). `devHooks.workspaceLoad`로 두 번째 프로젝트의 읽기를 늦추고, 그동안 새 작업그룹을 누른다.
그 프로젝트에는 저장소가 없어서 만들기를 부르면 "저장소 없음" 오류가 나는데, 오류가 나지 않아야 한다.

## 4. [P2] 이어 받아 쓰다가 실패 코드로 끝나도 새로 시작됨 — 타당, 수정 (사용자가 고르게)

**검증**: 소스. `resume || args`는 시작 실패와 쓰다가 끝난 것(Ctrl-C 130 등)을 구분하지 못한다.

**판단**: CLI를 해석하지 않고는 둘을 구분할 수 없다. 그래서 자동으로 새로 시작하지 않고, 터미널에서 물어본다.

**수정**: 이어서 하기가 0이 아닌 코드로 끝나면 `[ddak] Could not continue the previous session (exit N). Start a new one? [y/N]`
를 보이고, y일 때만 처음 인자로 띄운다. 기본은 시작하지 않는다 (그 뒤 셸이 남는다).

**확인**
- Rust `fallback_asks_before_starting_fresh`: 130으로 끝나면 묻고, y면 처음 명령, 빈 답이면 안 함, 성공하면 묻지 않음.
  묻기를 끄면 실패.
- 자체 테스트 (`resume-check`): 이어서 하기가 실패하는 세션은 묻고 바로 시작하지 않다가, y를 넣으면 같은 세션 ID로 처음
  인자로 뜬다.

## 5. [P2] codex는 창별 대화를 복원하지 못함 — 문제는 맞음, 한계로 남김 (합의 필요)

**검증**: codex 0.164 `--help`와 공식 CLI 문서에 새 대화를 시작할 때 세션 ID나 이름을 정하는 방법이 없다
(`resume`·`archive` 등은 ID·이름을 받지만 정하는 쪽은 없음). `--last`는 현재 폴더의 가장 최근 대화를 고른다.

**판단**: 창마다 정확히 이어 가려면 codex의 실제 세션 ID를 알아내야 한다. codex가 남기는 대화 파일을 읽거나, `-c`로 훅을
설정해 ID를 적게 하는 방법이 있다. 둘 다 ddak이 특정 CLI를 해석하는 일이고, 훅은 신뢰 설정도 걸린다. 기본 구성은 작업그룹
폴더마다 codex가 하나라서 `--last`가 맞게 동작한다. 그래서 지금은 한계로 밝혀 두고(설정 주석, 스펙), 같은 폴더에 codex를
둘 이상 쓰는 일이 실제로 생기면 그때 훅 방식을 검토하자고 제안한다.

## 그 밖

- **안내 정정**: 저장된 창은 저장한 세션 구성을 그대로 쓰므로, `groups.json`에 `resume`을 더해도 그 뒤에 만든 탭부터
  이어 받는다 (리뷰어 지적). 스펙에 적었다.
- **정상 종료 때 저장**: Cmd+Q는 시스템 종료 항목이라 창 닫기 이벤트를 거치지 않는다. 막으려면 종료 항목을 바꾸고 프론트를
  기다리는 장치가 필요해서, 대신 저장 시점을 당겼다. 탭·분할·이름 같은 변화는 바로 저장하고, 구분선 끌기만 0.3초 모은다.
  저장 요청이나 줄이 끝나기 전에 앱이 끝나면 그 변화는 잃을 수 있다 (후속 리뷰에서 정정).
- 목록에서 뺀 프로젝트의 상태를 남기는 정책은 리뷰어도 적절하다고 봤다.

## 후속 리뷰: Workspace가 다시 생길 때 2건 — 타당, 수정

리뷰어가 실제 Workspace를 마운트하고 IPC 응답을 늦춰 확인했다. 소스로도 맞다: 취소 검사는 마지막 dispatch에만 있었고,
저장 줄은 컴포넌트마다 따로 있어 언마운트 뒤에도 이어졌다.

### [P2] 취소된 읽기가 최신 저장 파일을 `.bad`로 옮김

**수정**: 읽기는 프로젝트의 줄(아래)에서 돈다. 정리된 Workspace면 읽기 전에, 읽은 뒤에, 오류일 때 모두 그만둔다 (파일을
치우지도, 알리지도, 상태를 바꾸지도 않는다).

**확인**: 자체 테스트 (`main`). other를 다시 넣으며 첫 읽기를 1.5초 늦추고 모양이 틀린 내용을 돌려준다. 끝난 뒤 상태 파일이
남아 있고(`.json` 1, `.json.bad` 1), 읽기 실패 알림이 없어야 한다. 읽은 뒤의 취소 검사를 끄면 실패.

### [P2] 이전 Workspace의 저장이 새 Workspace의 상태를 덮음

**수정**: 상태 파일의 읽기·치우기·저장을 프로젝트 경로마다 하나인 줄(모듈 전역 `inOrder`)에 세운다. 다시 생긴 Workspace의
읽기는 이전 인스턴스의 남은 저장이 끝난 뒤에 돌아서, 이전 인스턴스의 마지막 상태로 열리고, 그 뒤 저장은 덮이지 않는다.

**확인**: 자체 테스트 (`main`). 첫 저장을 1.5초 늦춘 채 other에 탭을 둘 더 열고 바로 뺐다 다시 넣는다. 탭 셋으로 열리고, 탭을
하나 더 연 뒤 파일과 화면의 탭 수가 같아야 한다. 저장을 인스턴스마다 따로 세우면 실패.

### 안내 정정

- codex 한계에 "같은 폴더에서 ddak 밖에서 띄운 codex"도 넣었다 (기본 구성이 하나라는 것만으로는 보장되지 않음).
- 종료 손실: 바로 저장해도 저장 요청이나 줄이 끝나기 전에 앱이 끝나면 구분선 말고 다른 변화도 잃을 수 있다고 고쳤다.
