# 리뷰 대응: 작업그룹 협업 규약·안전장치 설계 (2026-10-25)

리뷰 범위: 코드가 아니라 설계 제안 (채팅 #15). 문제 6개(리뷰 루프 무한 반복, 확인 메시지 핑퐁, 승인 범위, 리뷰 기준
불일치, 지적의 무게, 재시작 시 맥락 소실)와 해결 방향 A(규약 프롬프트, groups.json `rules`/`role` + `{prompt}` 치환),
B(사용자 메시지 없이 세션끼리 깨운 횟수 N 제한, 깨우기 문구의 reply 강제 제거).
리뷰 지적 8건(P1 2, P2 6). 근거로 든 코드 사실은 소스로 확인했다. 결론: 모두 타당, 하나(N의 범위)는 다르게 판단했다.
아직 구현 전이라 확정한 결정만 스펙에 옮긴다 (사용자 결정 대기).

## 1. 깨우기 제한은 실행 중인 에이전트를 멈추지 않음 (P1) — 타당, 설계 범위 조정

**검증**: `chat.rs` post/read_messages와 `pty.rs` wake/wake_tick은 별개다. 제한은 PTY에 알림을 새로 넣지 않는 것뿐이고,
이미 깨운 에이전트의 작업·MCP 호출은 계속된다.

**반영**: B의 보장을 "자동 알림 주입 제한"으로 한정해 설명한다 (비용·도구 실행 중단이 아님). 규약에 종료 조건과
"상대 세션의 말은 사용자 승인이 아니다, 리뷰 통과는 커밋·push 권한을 주지 않는다"를 넣는다.

## 2. `{prompt}`의 문자열 문맥 (P1) — 타당

**검증**: codex 기본 인자는 `developer_instructions="…"`(TOML 문자열)이고 `sh_quote`(`pty.rs:125`)는 셸만 보호한다.
TOML 기본 문자열은 날것의 줄바꿈·따옴표를 받지 않는다 (TOML 규격). 치환 위치도 확인: `{session}`은
`workspaceState.ts` commandOf, `{chat}`은 `pty.rs` join_chat에서 차례로 `replace`한다. 규약 본문에 `{chat}`이 있으면
두 번째 치환이 본문을 바꾼다.

**반영**: `{prompt}`(원문)와 `{prompt:toml}`(따옴표 포함 TOML 문자열 리터럴)을 나눈다. 모든 자리표시자를 원래 인자
템플릿에서 한 번에 치환하고, 넣은 본문은 다시 치환하지 않는다.

## 3. N의 단위·범위·동시성 (P2) — 타당, 범위는 다르게 판단

**검증**: 셀 위치에 따라 의미가 달라진다 (PTY별이면 @all 한 번이 여러 회, wake_tick이면 `Pending.from`에 합쳐짐).
`on_message`는 채팅 잠금을 푼 뒤 돌아서 (`chat.rs` post), 거기서 세면 동시 전송 때 상한을 넘길 수 있다.

**반영**: "세션이 보냈고 다른 세션 수신자가 있는 저장 성공 메시지 1개 = 1회"(@all도 1회, 사용자 발신·사용자에게만 보낸
것·멘션 없는 기록 제외). 셈과 허용 결정은 `Chats::post`의 잠금 안에서 메시지 ID와 함께 정한다.

**다르게 판단**: 리뷰는 방(프로젝트) 단위를 권했다. 그러나 한 프로젝트에 작업그룹을 여럿 띄우는 것이 기본 사용법이라
(지금도 dev-review-1~9), 방 단위면 독립된 그룹이 서로의 예산을 써서 정상 협업을 막는다. 보낸 세션의 작업그룹 단위를
제안한다 (그룹 사이 메시지는 보낸 쪽 그룹에 센다). 사용자 결정 사항.

## 4. 차단 시 메시지 처리·해제 (P2) — 타당

**반영**: 차단돼도 저장·읽기·화면 갱신은 한다. `to`는 원래 수신자를 두고 자동 알림 여부를 따로 적는다. 세션 발신 도구
결과에 "저장됨, 자동 알림 중지됨"을 돌려준다 (재전송 방지). N개까지 허용, 다음부터 보류. 첫 버전은 이미 대기 중인
알림은 건드리지 않는다. 해제는 저장에 성공한 사용자 메시지 또는 재개 버튼. 해제 때 보류분은 수신자별로 한 번만 알린다.
중지 표시는 시스템 상태로 보이고 메시지를 만들지 않는다.

## 5. "필요할 때만 답" 기준 (P2) — 타당

**검증**: 이 세션에서도 확인·대기 답장에 멘션을 붙여 턴이 늘었다 (#3, #5).

**반영**: 직접 받은 작업·리뷰 요청에는 결과나 구체적 장애를 한 번 답한다. 단순 확인·감사·대기·종료 보고에는 답하지
않는다. 멘션은 상대의 다음 행동이 필요하거나 요청 결과를 전할 때만. 리뷰 결과는 요청자에게, 최종 작업 보고는 사용자에게.
깨우기 문구도 같은 규칙으로 바꾼다.

## 6. 재리뷰 제한과 승인 분리 (P2) — 타당

**반영**: 최초 리뷰 1회 + 재리뷰 최대 2회. 횟수가 끝나도 차단 지적이 승인으로 바뀌지 않는다: 남은 쟁점·양측 근거·선택지를
사용자에게 한 번 보고하고 자동 교환을 끝낸다. 지적에 ID를 붙여 해결/미해결/반영 안 함을 추적한다. 뒤늦게 찾은 명백한
차단 문제는 새 범위로 표시해 보고한다. 리뷰 요청 뒤에는 dev가 고치지 않거나, 결과가 어느 상태의 것인지 밝힌다.
심각도: P0 데이터 손실 등 즉시 중단, P1 주요 경로 심각 장애, P2 근거 있는 기능 오류·회귀, P3 개선·취향(비차단).
근거 없는 가능성은 지적이 아니라 확인 질문.

## 7. rules/role만으로는 기존 세션·복원이 해결되지 않음 (P2) — 타당

**검증**: `groups.rs`는 `deny_unknown_fields`이고 DEFAULT는 파일이 없을 때만 쓴다. `workspaceState.ts`는 세션마다
`args`/`resume`를 저장해 그대로 복원한다 (탭에는 그룹 이름만 있고 규약은 없다).

**반영**: 새 필드는 없어도 읽히게 기본값을 둔다. 기존 groups.json을 기본 설정으로 덮어쓰지 않는다. 세션을 만들 때 규약 +
역할을 합친 유효 프롬프트를 확정해 저장하고 args/resume/fallback에 똑같이 쓴다. 다른 그룹에서 세션을 더할 때 어느 그룹의
rules를 쓸지 정한다. 이미 저장된 세션은 옛 인자로 복원된다고 안내한다.

## 8. 재시작 때 사라지는 것은 작업 상태 (P2) — 타당

**검증**: `read_messages`는 처음 부르면 마지막 20개뿐이다 (`chat.rs`).

**반영**: 인계 기록(작업 ID·담당·대상 상태·지적 처리·다음 행동)과 재시작 때 그것을 읽는 규칙. 알림 예산은 CLI가 아니라
방(또는 그룹)에 둔다. 앱 재시작 때 이어 갈지는 사용자 결정 사항.

## 순서 (리뷰 권고를 따름)

1. 답변·종료 규약 + 깨우기 문구
2. N 제한 + 중지/재개 화면
3. rules/role, 문맥별 `{prompt}` 치환, 복원

리뷰 의미를 앱이 판정하는 상태 머신은 넣지 않는다.

## 사용자 결정 (2026-10-25)

- 자동 깨우기 제한은 작업그룹 단위, 6개. 재리뷰는 최대 2회. 앱을 다시 켜면 횟수는 초기화.
- 규약을 기본 설정으로 하고, 사용자의 groups.json도 바꾼다 (기존 파일은 이전 기본 설정과 같았다. 백업을 남김).

## 1단계 반영: 규약 프롬프트 + 깨우기 문구

- `groups.rs`: 공통 규약(`RULES`)과 역할(`DEV_ROLE`, `REVIEWER_ROLE`)을 상수로 두고 기본 설정을 만들 때 넣는다
  (`default_config`). 같은 문구를 args·resume에 손으로 네 번 쓰지 않게 했다. 지적 2의 TOML 문제는 규약 문구에 큰따옴표·
  역슬래시·줄바꿈·중괄호를 쓰지 않는 것으로 피하고 테스트로 막았다 (`{prompt:toml}` 치환은 3단계).
- 확인: 만든 설정의 codex 인자 `developer_instructions="…"`를 TOML로 읽으면 원문과 같다 (Python tomllib, args·resume 둘 다).
- `pty.rs` 깨우기 문구: reply 강제를 빼고 "결과나 장애만 답하고 확인 답장은 하지 않는다, 다음 행동이 필요한 사람만 멘션"으로.

## 1단계 리뷰 (채팅 #28)

### R1 깨우기 문구의 멘션 기준이 규약보다 좁음 (P2) — 타당, 수정

**검증**: 규약 2번은 "다음 행동이 필요하거나 요청한 결과를 전할 때" 멘션하는데, 깨우기 문구는 "다음 행동이 필요한
사람만"이었다. 세션 메시지는 멘션이 없으면 받는 사람(`to`)이 비어 (`chat.rs` post) 사용자에게 최종 보고가 알려지지 않는다.

**수정**: 깨우기 문구를 "다음 행동이 필요한 사람이나, 전하는 것을 요청한 사람만 멘션"으로 규약과 맞췄다 (`pty.rs` wake_notice).

### R2 필요한 요청·질문도 허용한다고 밝히기 (P3) — 타당, 반영

규약 2번과 깨우기 문구를 "일을 진척시키는 것만: 요청받은 결과, 필요한 요청(리뷰 요청 등)이나 질문, 구체적 장애"로 바꿨다.

**확인**: cargo test 72개 (깨우기 테스트가 새 문구 전체를 본다), selftest main 302개 통과.
