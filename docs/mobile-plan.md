## 유저 스토리

> 사용자는 모바일 기기에서 프로젝트를 선택하고 채팅창에서 열린 세션에 명령하고 결과를 알림으로 받을 수 있다.

사용자는 같은 사람이 여러 컴퓨터(맥북, 데스크톱 등)에서 ddak을 쓴다. 그래서 폰에서는 **컴퓨터 → 프로젝트 → 채팅** 순으로 고른다.

풀어 쓰면:

0. 폰에서 연결한 컴퓨터 목록을 본다 (켜져 있는지, 컴퓨터마다 안 읽은 수·기다리는 세션 수). 하나를 고른다.
1. 그 컴퓨터의 ddak 프로젝트 목록을 본다 (안 읽은 수, 열린 세션 수, 사용자를 기다리는 세션 표시).
2. 프로젝트를 고르면 그 프로젝트의 채팅방이 열린다. 데스크톱 채팅 패널과 같은 방, 같은 메시지다.
3. 참여자 칩(열린 세션)을 눌러 `@이름`을 넣고 보낸다. 데스크톱 채팅에서 `user`로 보낸 것과 똑같이 저장·깨우기가 된다.
4. 세션이 `@user`로 결과·질문·커밋 준비를 알리거나, 세션이 사용자를 기다리게 되면 폰에 푸시 알림이 온다.
   어느 컴퓨터에서 왔는지 알림에 보이고, 누르면 그 컴퓨터의 그 프로젝트 채팅이 열린다.

### 범위

포함
- 컴퓨터 목록·선택, 프로젝트 목록, 채팅 읽기·보내기, 참여자와 상태 보기, 푸시 알림, 컴퓨터마다 연결(페어링)·해제

여러 컴퓨터를 하나로 합치지는 않는다: 프로젝트·채팅방·세션은 지금처럼 컴퓨터마다 따로다 (같은 저장소를 두 컴퓨터에서
열어도 채팅방은 둘). 폰이 여러 컴퓨터를 나란히 보여 줄 뿐이다. 컴퓨터끼리 동기화는 하지 않는다.
- 아직 열지 않은 프로젝트를 폰에서 고르면 데스크톱에서 그 프로젝트를 열어 세션을 복원 (아래 M2, 결정 D4)

제외 (나중 후보)
- 터미널 화면 보기·직접 입력, 권한 확인(도구 승인)에 폰에서 답하기 (결정 D3)
- 폰에서 작업그룹 만들기·끝내기, 파일 보기, Git Graph
- ddak이 꺼져 있거나 맥이 잠든 동안의 동작 (아래 "제약")

## 지금 있는 것 (출발점)

모바일 기능은 이미 있는 채팅방·알림 경로에 "입구"와 "출구"를 하나씩 더하는 일이다.

| 필요한 것 | 지금 코드 |
|---|---|
| 메시지 보내기 (사용자로) | `Chats::post(project, "user", text)` — `chat_post`가 쓰는 것. 멘션 해석·받는 사람·깨우기·자동 깨우기 제한 풀기가 모두 여기서 된다 |
| 메시지 읽기 | `Chats::messages(project)` (파일 전체를 읽음. 모바일용으로 `since`·`limit` 필요) |
| 참여자 = 열린 세션 | `Chats::members(project)` |
| 새 메시지 감지 | `Chats::start`의 `on_message` 콜백 → 지금은 프론트 `chat` 이벤트 |
| 알림을 보낼 때 | `notify::send(project, kind, body)` — 채팅 `@user`, 자동 깨우기 멈춤, 기다림(`attention`) |
| 보고 있는지 | `notify::set_view`·`set_focused` (데스크톱 기준) |
| 안 읽은 수 | 프론트가 세고 `set_badge`로 Dock에 표시 |
| 세션 상태 (작업 중·대기 등) | 프론트 `programStatus.ts`. Rust는 `awaiting`만 안다 (`pty_awaiting`) |
| 프로젝트 목록 | `projects.json` (프론트가 내용을 정함, Rust는 읽고 쓰기만) |

## 제약

- **맥에서 ddak이 돌고 있어야 한다.** 세션(CLI)이 맥의 PTY에서 돈다. 폰은 원격 조종기일 뿐이다.
- **맥이 잠들면 끊긴다.** 노트북 덮개를 닫으면 (외부 디스플레이·전원 없이는) 잠든다. 열어 둔 상태의 유휴 잠자기는
  앱이 막을 수 있다 (아래 "설정 화면"의 잠자기 막기, M4).
- **폰에서 보낸 메시지 = 에이전트에게 내리는 명령 = 맥에서 셸 명령 실행 권한.** 그래서 이 입구는 원격 코드 실행
  통로와 같은 무게로 다룬다. 공개 인터넷에 열지 않고, 기기 인증을 둘 겹으로 둔다.
- **공개 저장소·팀 배포.** 사용자마다 자기 맥·폰을 잇는 구조여야 한다. 공용 서버나 저장소에 넣는 비밀 키
  (APNs 키, 봇 토큰 등)가 필요한 방식은 배포할 때 문제가 된다.
- 채팅 MCP 서버는 지금처럼 127.0.0.1에만, Host·Origin 검사도 그대로 둔다. 모바일 입구는 따로 만든다.
- **컴퓨터가 여러 대.** 폰 앱 하나가 여러 ddak에 붙어야 하고, 어느 컴퓨터가 꺼져 있어도 나머지는 써야 한다.
  특정 컴퓨터가 "중심"이 되면 안 된다 (그 컴퓨터가 꺼지면 전부 못 씀).
- ddak은 지금 macOS 전용이다 (알림 센터, `clonefile`, `setsid` 등). 나중에 Windows도 쓸 수 있지만 지금은 맥만 연결한다
  (D8 결정). 모바일 서버·API·폰 앱에는 macOS에만 있는 것을 넣지 않아, Windows ddak이 생기면 같은 폰 앱에 붙게 한다.

## 방식 비교

두 가지를 정해야 한다: **폰이 맥에 어떻게 닿는가(연결)** 와 **폰에서 무엇으로 보는가(클라이언트·알림)**.

### 연결

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. Tailscale (추천)** | 맥·폰을 같은 tailnet에. `tailscale serve`가 HTTPS(`*.ts.net` 인증서)로 받아 127.0.0.1의 ddak 모바일 서버로 넘긴다 | 포트 열기·서버 없음. 인터넷에 노출되지 않음. HTTPS 자동 (PWA·Web Push에 필요). 요청에 tailnet 사용자 신원 헤더 | 맥·폰에 Tailscale 앱과 계정 필요 (개인 무료) |
| B. Cloudflare Tunnel + Access | 공개 호스트 이름을 Access(로그인)로 막음 | 폰에 앱 설치 없음 | 도메인·Cloudflare 설정 필요. 공개 주소라 설정 실수가 곧 노출 |
| C. 자체 중계 서버 | ddak이 밖으로 WebSocket을 열고 폰은 중계 서버에 접속 | 아무 네트워크에서나 됨 | 서버 운영·인증·종단 암호화를 직접. 팀 배포 시 누가 운영하나 |
| D. 메신저 봇 (Telegram 등) | ddak이 봇 API를 롱 폴링, 메시지를 채팅방과 이어 줌 | 가장 빠름. 알림·앱이 공짜. 들어오는 포트 없음 | 코드·대화가 제3자 서버를 지남. 봇 토큰 관리. 표현 제한(멘션 칩, 상태). 프로젝트 선택이 명령어·토픽으로 어색함 |

### 클라이언트 · 알림

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **1. PWA + Web Push (추천)** | 모바일 웹 화면(정적 파일, 어디서 받는지는 아래 "여러 컴퓨터")이 ddak API를 부른다. 폰에서 홈 화면에 추가. 알림은 표준 Web Push (VAPID) | 같은 React·i18n·테마 코드 재사용. 스토어·서명 없음. 맥이 Apple·Google 푸시 서비스로 바로 보냄 (우리 서버 없음). 알림 내용은 기기 키로 암호화되어 푸시 서비스가 못 읽음 | iOS는 16.4+이고 홈 화면에 추가한 경우만 푸시. 백그라운드에서 연결 유지 안 됨 (열 때 다시 읽기) |
| 2. 네이티브 앱 (React Native) + APNs/FCM | 스토어 또는 TestFlight 배포 | 푸시·백그라운드 가장 안정적 | APNs 키를 각 맥에 둘 수 없어 결국 중계 서버 필요. 앱 심사·배포 비용. 화면 코드 재사용 적음 |
| 3. 메신저 앱 (D와 짝) | 봇 대화방이 곧 UI | 만들 화면이 없음 | 위 D의 단점 |
| 4. Claude Code 원격 기능 | claude 자체의 원격 이어 하기 | 만들 것이 없음 | claude 세션 하나씩만. codex·작업그룹·ddak 채팅방과 무관. 이 스토리("채팅방에서 세션에 명령")와 다름 |

### 추천: A + 1 (Tailscale + ddak이 제공하는 PWA + Web Push)

- 비밀 키·서버 없이 사용자마다 자기 맥에서 끝난다 (팀 배포와 맞음).
- 메시지는 tailnet 안에서만, 알림 내용은 종단 암호화로 오간다.
- 채팅 기능이 Rust(`Chats`)에 이미 모여 있어서, 모바일 서버는 얇은 HTTP 겉면이다.
- 화면은 지금 프론트의 i18n·테마·채팅 표시 규칙을 다시 쓴다.
- 여러 컴퓨터: 같은 Tailscale 계정에 모든 컴퓨터와 폰을 넣으면 폰에서 컴퓨터마다 `https://<컴퓨터>.<tailnet>.ts.net`로 닿는다.
- 나중에 Tailscale 대신 B를 원하면 모바일 서버는 그대로 두고 앞단만 바꾼다.

빠르게 알림만 먼저 받고 싶다면 D(Telegram)를 임시로 붙이는 길도 있지만, 대화 내용이 밖으로 나가고 결국 버릴
코드라서 추천하지 않는다.

### 서버(Firebase 등)와 네이티브 앱(Flutter)을 쓰는 안

서버와 크로스플랫폼 앱도 쓸 수 있다는 전제로, 가장 흔한 조합을 끝까지 그려 보고 추천안과 비교했다.

**E. Firebase(Auth + Firestore + FCM + Cloud Functions) + Flutter 앱**
- ddak이 Firestore에 채팅 메시지를 올리고 폰 명령을 Firestore에서 받는다. 로그인(Google 계정)으로 여러 컴퓨터·폰이 묶인다.
  메시지가 생기면 Cloud Function이 FCM(→ APNs)으로 푸시한다. 폰은 Flutter 앱.
- 좋은 점: Tailscale 없이 어디서나 된다. 네이티브 푸시가 가장 안정적이다. 컴퓨터 목록이 계정에서 저절로 나온다.
- 나쁜 점:
  - 새로 만들 것이 많다: Flutter 앱(화면·로그인·푸시), Firebase 프로젝트·보안 규칙·Cloud Function(유료 Blaze 요금제),
    ddak의 Google 로그인(OAuth 루프백)과 Firestore 클라이언트 (Rust 공식 SDK 없음, REST로는 실시간 구독이 안 돼 폴링).
  - 채팅 내용(코드·경로 포함)과 "명령"이 클라우드 DB를 지난다. Firebase 계정이 털리면 모든 맥에 원격 명령을 내릴 수 있다.
  - 팀 배포 때 팀원 데이터가 누구의 Firebase에 쌓이는지 정해야 한다. iOS 앱은 TestFlight·App Store 배포가 필요하다.
  - 앱과 ddak 사이 동기화(누가 원본인지, 끊겼다 이어질 때)를 새로 설계해야 한다. 지금 채팅은 맥의 JSONL 하나가 원본이다.
- 판단: 추천안보다 만들 것이 3~4배이고, 보안 경계를 클라우드로 넓힌다. 얻는 것(VPN 없이 접속, 푸시 안정성)은 아래
  "단계적 대안"으로 필요한 만큼만 살 수 있다. **채택하지 않는다.**

**F. 자체 웹 서버(중계) + PWA 또는 Flutter**: E와 같은 구조에서 Firebase 대신 직접 운영한다. 운영·인증·종단 암호화까지
직접이라 E보다 무겁다. 채택하지 않는다.

**Flutter만 (Tailscale 위에서, 서버 없이)**: 화면은 Flutter로도 되지만, 네이티브 푸시(APNs)를 보내려면 Apple 키가 필요하고
그 키를 사용자마다 맥에 둘 수 없어 결국 푸시 중계 서버가 따라온다. 웹앱으로 부족한 것이 확인되기 전에는 이득이 없다.

### 단계적 대안 (M0에서 웹앱이 부족하다고 나오면)

처음부터 무겁게 가지 않고, M0 실험에서 막힌 것만 그만큼 바꾼다.

| M0에서 막힌 것 | 바꾸는 것 | 그대로인 것 |
|---|---|---|
| Web Push가 안 오거나 자주 끊김 | 폰 앱만 Flutter로 + **푸시만** 작은 중계(Firebase Cloud Function 하나 또는 FCM). 중계에는 "알림 문구 + 컴퓨터·프로젝트 id"만 보낸다 | 데이터·명령은 Tailscale로 맥에 직접. 맥의 모바일 서버·API |
| 고정 주소 화면이 각 컴퓨터를 부르지 못함 (CORS·Chrome 로컬 네트워크 접근 권한) | Flutter 앱 (브라우저 출처 제약이 없음). 단 Android의 로컬 네트워크 권한이 Tailscale 주소에 걸리는지 먼저 시험한다 | 나머지 전부 |
| 위 Flutter 대안도 막힘 | 사용자에게 요구 완화를 묻는다: "나"(주 컴퓨터가 화면을 내줌)는 주 컴퓨터가 꺼지면 앱을 처음 열 수 없어 "어느 컴퓨터가 꺼져도 나머지는 쓴다"를 채우지 못한다 | — |
| Tailscale 설치가 너무 번거로움 (팀 배포 때) | 그때 E를 다시 검토 | — |

API를 처음부터 화면과 분리해 두므로 (JSON over HTTPS), 폰 앱을 Flutter로 바꿔도 맥 쪽은 거의 그대로다.

### 여러 컴퓨터: 폰 앱(PWA)을 어디서 내려받나

PWA는 "출처(origin)"마다 따로다 (홈 화면 아이콘, 저장소, 서비스 워커, 푸시 구독이 모두 출처별). 컴퓨터마다 자기
주소에서 화면을 내주면 폰에 컴퓨터 수만큼 아이콘이 생기고 앱 안에서 컴퓨터를 고를 수 없다. 그래서 화면은 한 출처에서
받고, 데이터는 컴퓨터마다 직접 받는다.

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **가. 정적 클라이언트를 고정 주소에 (추천)** | 모바일 화면(HTML·JS만, 데이터 없음)을 GitHub Pages 같은 고정 주소에 둔다. 화면이 각 컴퓨터의 `*.ts.net` API를 직접 부른다 (CORS) | 중심 컴퓨터 없음. 아이콘 하나. 어느 컴퓨터가 꺼져도 나머지는 됨 | 화면 코드가 제3자 호스팅에 있음 (바뀌면 토큰을 훔칠 수 있다 → 아래 대책). 화면과 ddak 버전이 따로 놀 수 있음 (API 버전 확인). Android Chrome의 로컬 네트워크 접근 제한에 걸릴 수 있음 (M0 확인) |
| 나. 한 컴퓨터가 화면을 내줌 | "주 컴퓨터"의 ddak이 화면을 내주고, 다른 컴퓨터는 CORS로 부름 | 제3자 호스팅 없음 | 주 컴퓨터가 꺼지면 처음 열기가 안 됨 → "어느 컴퓨터가 꺼져도 나머지는 쓴다"를 채우지 못한다 (요구 완화라 사용자 결정 필요). 주 컴퓨터를 바꾸면 폰 앱을 다시 설치 |
| 다. 컴퓨터마다 따로 | 각 ddak이 자기 화면을 내줌 | 가장 단순 | 앱 안에서 컴퓨터 선택 불가 (아이콘 여러 개). 요구 사항을 못 채움 |

추천은 **가**. 이때 무엇을 믿는 것인지 정확히 적는다 (D7):
- **화면 배포 경로 = 연결한 모든 맥의 원격 명령 권한.** 한 출처의 저장소에 모든 컴퓨터의 기기 토큰이 있고, 바뀐 화면
  코드는 사용자의 폰 안에서 그 폰의 Tailscale 신원으로 각 컴퓨터에 직접 요청한다. 그래서 컴퓨터별 토큰·Tailscale 신원
  확인은 이 위협을 막지 못한다. 화면을 바꿀 수 있는 사람·계정(GitHub 저장소 쓰기 권한, Actions, Pages 설정)을 그만큼
  믿는다는 결정이다.
- 줄이는 방법: 화면은 이 공개 저장소에서 GitHub Actions로만 빌드·배포한다 (사람이 올리지 않음). 코드는 공개라 확인할 수
  있다. 저장소 쓰기 권한은 사용자만 갖는다.
- 위와 구별되는 **토큰 하나가 새는 경우**(폰 분실 등)는 피해가 그 컴퓨터로 한정되고, 데스크톱에서 그 기기를 해제하면 끝난다.
  Tailscale 신원 확인이 있어서 토큰만으로는 tailnet 밖에서 쓸 수 없다.
- 화면은 "어디서 받았는지"에 의존하지 않게 만든다 (API 주소는 모두 페어링 때 받은 것). 그래야 대안으로 옮기기 쉽다.

### 여러 컴퓨터: 푸시 알림

Web Push 구독은 서비스 워커(출처) 하나에 하나이고, 구독은 VAPID 공개 키 하나에 묶인다. 보내는 쪽은 그 짝인 개인 키로
서명해야 한다. 여러 컴퓨터가 한 폰에 보내려면 모두 같은 키를 써야 한다.

- **키는 폰이 만든다.** PWA가 처음 켜질 때 WebCrypto로 P-256 키 쌍을 만들고 그 공개 키로 푸시를 구독한다.
- 컴퓨터와 페어링할 때 폰이 그 컴퓨터에 (구독 정보 + 개인 키)를 보낸다 (Tailscale HTTPS 위, 기기 토큰으로 인증된 요청).
  컴퓨터는 앱 데이터에 0600으로 둔다.
- 이 키로 할 수 있는 일은 "이 폰에 알림 보내기"뿐이다 (여러 보내는 쪽이 같은 VAPID 키를 쓰는 것은 RFC 8292와 충돌하지 않는다).
- **푸시 권한 회수 = 폰의 "알림 키 바꾸기".** 폰 목록에서 컴퓨터를 빼는 것만으로는 회수가 아니다 (그 컴퓨터가 꺼져 있으면
  사본을 지울 수 없다). 폰에서 컴퓨터를 빼면 폰이 이어서: 지금 구독을 해지(unsubscribe) → 새 키 쌍 → 새 구독 → 남은
  컴퓨터들에 새 (구독, 키)를 보낸다. 예전 구독 주소가 없어지므로 뺀 컴퓨터의 사본은 쓸모가 없다. 그때 꺼져 있던 남은
  컴퓨터는 다음에 연결될 때 받는다 (그 전까지는 그 컴퓨터의 알림이 오지 않는다고 폰에 보인다).
  컴퓨터 쪽에서 기기를 해제하면 그 컴퓨터는 사본과 토큰 해시를 지운다 (그 컴퓨터만의 회수).
- 대안: 컴퓨터마다 서비스 워커 범위를 따로 두어 구독을 여러 개 만드는 방식. 키를 나누지 않아도 되지만 브라우저마다
  되는지 확실하지 않아 M0에서만 시험한다.

## 추천안 설계

```
iPhone / Android
 └ PWA (화면만, 고정 주소에서 받음)
     폰 저장소: 컴퓨터 목록 [{이름, 주소, 기기 토큰}], 푸시 키 쌍
     │
     ├─ HTTPS ─→ https://macbook.<tailnet>.ts.net ─┐
     └─ HTTPS ─→ https://studio.<tailnet>.ts.net  ─┤ (컴퓨터마다 같은 구조)
                                                   ▼
tailscale serve (각 컴퓨터) ── 신원 헤더 Tailscale-User-Login 추가
   │  http://127.0.0.1:<모바일 포트>
   ▼
ddak 앱
 ├─ mobile.rs: 모바일 HTTP 서버 (새로, 127.0.0.1 고정 포트)
 │    ├─ /api/…: 컴퓨터 정보·프로젝트·메시지·참여자·보내기·페어링·푸시 구독
 │    └─ /api/events: SSE (새 메시지·참여자·상태)
 ├─ chat.rs (Chats): 그대로. on_message를 프론트 + 모바일로 나눠 보냄
 ├─ notify.rs: 보내는 곳에 "모바일 푸시" 추가 (보내는 규칙은 아래)
 └─ push.rs: Web Push (VAPID 키, 구독 목록, 암호화, 전송)
          │  HTTPS
          ▼
   Apple / Google / Mozilla 푸시 서비스 → 폰 알림
```

### 모바일 서버 (`mobile.rs`)

- MCP 서버와 다른 리스너. 인증 모델(기기 토큰)과 Host 규칙이 달라서 섞지 않는다.
- 127.0.0.1에만 묶는다. 밖에서는 `tailscale serve`를 거쳐서만 들어온다 (Tailscale IP에 직접 묶지 않는다:
  HTTPS가 없고 신원 헤더도 없다).
- 포트는 고정값(설정, 예: 47320)을 쓴다. MCP처럼 매번 바뀌면 `tailscale serve` 설정을 매번 다시 해야 한다.
  포트를 쓸 수 없으면 모바일 연결만 꺼지고 알린다.
- 기본은 꺼짐. "모바일 연결" 설정에서 켤 때만 띄운다.
- `tiny_http`를 그대로 쓴다 (기기 1~2대라 연결마다 스레드여도 된다). SSE는 응답 본문을 스트림으로 쓴다.
  부족하면 그때 바꾼다.
- 폰은 SSE를 `EventSource`가 아니라 `fetch` 스트림으로 받는다 (`EventSource`는 `Authorization` 헤더를 넣을 수 없다.
  토큰을 URL에 싣지 않는다).

### API (초안)

| 요청 | 내용 |
|---|---|
| `GET /api/info` | 컴퓨터 이름(사용자가 정함, 기본은 컴퓨터 이름), 컴퓨터 id, ddak 버전, API 버전, 전체 안 읽은 수·기다리는 세션 수. 폰의 컴퓨터 목록이 이것으로 켜짐/꺼짐을 본다 |
| `POST /api/pair` | 페어링 코드 → 기기 토큰 발급 |
| `GET /api/projects` | 목록: id, 이름, 열림 여부, 참여 세션 수, 안 읽은 수, 기다리는 세션 수 |
| `POST /api/projects/:id/open` | 데스크톱에서 그 프로젝트 Workspace를 만들게 함 (세션 복원) |
| `GET /api/projects/:id/messages?before=&limit=` | 메시지 (최신부터 페이지) |
| `POST /api/projects/:id/messages` | `user`로 보냄 → `Chats::post` |
| `GET /api/projects/:id/members` | 참여자 + 상태(작업 중·기다림·완료·오류) + 깨우기 대기 여부 |
| `POST /api/projects/:id/read` | 여기까지 읽음 (안 읽은 수 지우기) |
| `POST /api/projects/:id/resume` | 자동 깨우기 재개 (`chat_resume`과 같음) |
| `GET /api/events` | SSE: `message`, `members`, `status`, `unread`, `paused` |
| `POST/DELETE /api/push` | Web Push 구독 등록·해제 |

- 프로젝트 id는 경로가 아니라 채팅 파일 이름과 같은 `<이름>-<경로 해시>`. URL에 경로를 싣지 않는다.
  폰 화면의 주소는 `#/<컴퓨터 id>/<프로젝트 id>`.
- 컴퓨터 id는 설치마다 한 번 만드는 난수 (앱 데이터). 컴퓨터 이름이나 Tailscale 이름이 바뀌어도 같은 컴퓨터로 본다.
- CORS: 허용 출처는 설정의 화면 주소 하나 (기본은 공식 화면 주소). `Authorization` 헤더를 쓰므로 미리 보내기(preflight)에 답한다.
- 화면은 `/api/info`의 API 버전이 모르는 것이면 그 컴퓨터를 "ddak 업데이트 필요"로 보이고 쓰지 않는다.
- 메시지 표시 규칙(보낸 사람, 받는 사람, `held`의 "알림 안 함", 내게 온 것 강조)은 데스크톱 채팅 패널과 같게 한다.

### 인증 · 보안

이 입구는 원격 명령 실행과 같으므로 다음을 모두 지킨다.

1. **기기 페어링 (컴퓨터마다)**: 데스크톱 "모바일 연결" 창에 QR(화면 주소 + 이 컴퓨터의 API 주소 + 5분짜리 1회용 코드)을
   띄운다. 폰으로 찍으면 PWA가 열려 코드를 기기 토큰(256비트 난수)으로 바꾸고, 컴퓨터 목록에 더한다. 두 번째 컴퓨터도 같은
   방법으로 더한다. 컴퓨터의 앱 데이터 `mobile/devices.json`에는 토큰의 해시·기기 이름·만든 시각·마지막 사용만 둔다.
   (QR을 카메라 앱으로 찍으면 설치한 PWA가 아니라 브라우저 탭으로 열릴 수 있다. iOS는 홈 화면 PWA와 Safari의 저장소가
   따로라 확실히 그렇다. 그래서 두 번째 컴퓨터부터는 PWA 안의 "컴퓨터 추가"에서 찍거나 코드를 붙여넣는 것을 기본으로 한다.
   Android에서 QR → 설치한 PWA로 이어지는지는 M0에서 확인.)
2. **요청 종류별 검사 순서** (모든 요청에 먼저 4번 Host 검사):
   - `OPTIONS` (CORS 미리 보내기): 브라우저는 여기에 토큰을 싣지 않는다. Origin·요청 메서드·요청 헤더가 허용 목록에 있는지만
     보고 데이터 없이 CORS 헤더만 답한다. 아니면 403.
   - `POST /api/pair`: 아직 토큰이 없으므로 1회용 페어링 코드로 인증한다 (+ Origin, Tailscale 신원 헤더가 있어야 함).
     코드는 한 번 쓰면 버린다. 이 요청이 이 컴퓨터에 처음 기록되는 Tailscale 로그인을 정한다.
   - 그 밖의 모든 요청: Origin + `Authorization: Bearer <기기 토큰>` + Tailscale 신원(3번)이 모두 맞아야 한다.
   쿠키를 쓰지 않으므로 CSRF가 없다. 토큰은 PWA 저장소(IndexedDB)에.
3. **Tailscale 신원 확인**: `Tailscale-User-Login` 헤더가 페어링 때 기록한 로그인과 같아야 한다. 헤더가 없으면
   (`tailscale serve`를 거치지 않은 요청) 거절한다. tailnet을 남과 같이 쓰는 경우에도 막힌다.
   (헤더는 127.0.0.1로 들어온 요청에서만 믿는다. 같은 맥의 다른 프로세스는 위조할 수 있지만 그 경우 기기 토큰도 필요하다.)
4. **Host·Origin**: Host는 이 컴퓨터의 `*.ts.net` 이름만 (DNS 리바인딩), Origin은 설정의 화면 주소만 받는다.
5. **`tailscale funnel`(공개 노출)은 쓰지 않는다**. 켜져 있으면 연결 창에 경고하고 모바일 서버를 멈춘다.
6. 기기 목록과 해제 버튼. 해제하면 그 기기의 푸시 구독도 지운다.
7. 페어링 시도·인증 실패를 세고 (예: 분당 10회) 넘으면 잠시 막는다. 모바일에서 보낸 메시지는 지금처럼 `user`로
   기록하되 출처(기기 이름)를 메시지에 남긴다 (`via` 필드, 데스크톱에는 작은 표시).
8. **Tailnet Lock + 키 만료** (Tailscale 설정, 사용자가 켬): Tailscale 로그인(Google 등)이 털리거나 Tailscale
   제어 서버가 공격받아도 남의 기기가 tailnet에 들어오지 못하게 한다. Tailnet Lock을 켜면 이미 믿는 기기가 서명해야 새 기기가
   들어온다. 기기 키 만료도 켠다. 이것이 없으면 로그인 하나로 tailnet에 들어와 모바일 서버까지 닿고, 남는
   방어는 기기 토큰(1번·2번) 한 겹이다. 관리 콘솔의 "새 기기 승인"은 Tailnet Lock과 함께 켤 수 없다 (2026-10-26 `lock init`이
   "cannot use Tailnet Lock and device approval at the same time"으로 거절). 서명이 승인보다 강하므로(제어 서버를 믿지 않아도
   됨) 승인은 끄고 Lock을 쓴다.
9. **Tailscale 접근 규칙(ACL)**: 폰 → 맥의 HTTPS(443, `tailscale serve`)만 허용한다. 맥 → 폰이나 다른 포트는 열지 않는다.
   모바일 연결 창은 이 규칙의 예시를 보여 준다 (규칙은 사용자가 관리 콘솔에 넣는다. ddak은 Tailscale 계정을 다루지 않는다).
- 전제: Google·GitHub 계정은 패스키나 2단계 인증을 쓴다. GitHub는 화면 배포 경로(D7)라 특히 중요하다.

### 푸시 알림 (`push.rs`, `notify.rs`)

- 표준 Web Push. VAPID 키는 폰이 만들어 페어링 때 받는다 (위 "여러 컴퓨터: 푸시 알림"). 폰마다 (구독, 키)를 둔다.
  저장소·번들에 키가 없다.
- 구현은 Rust `web-push` 크레이트 또는 `ece`(RFC 8291 암호화) + 직접 요청. M0에서 Android Chrome으로 실제 전달을 확인하고 고른다.
- 알림 내용: 컴퓨터가 둘 이상이면 제목에 컴퓨터 이름을 넣는다 (`ddak · <컴퓨터> · <프로젝트>`), 본문은 지금과 같은
  `<보낸 사람>: <첫 줄>`. 데이터에 컴퓨터 id·프로젝트 id를 넣어 누르면 그 채팅으로 연다. 같은 컴퓨터·프로젝트의 알림은
  `tag`로 묶어 쌓이지 않게 한다.
- 푸시 서비스가 404·410을 주면 그 구독을 지운다.
- **어디로 보낼지** (결정 D2. 추천안):
  - 맥 배너는 지금 규칙(`notify.rs` watching) 그대로 둔다: 창이 앞에 있고 그 프로젝트를 보고 있으면 생략하되, `Chat`
    종류(`@user` 메시지, 자동 깨우기 멈춤)는 그 프로젝트의 채팅 패널까지 열려 있어야 생략하고, `Attention`(기다림·권한
    확인)은 프로젝트만 보고 있어도 생략한다.
  - 폰 푸시도 같은 조건으로 생략한다 (맥에서 보고 있는 것은 폰에도 보내지 않음). 거기에 더해 폰 화면이 그 프로젝트 채팅을
    열어 두고 있으면 (SSE 연결 + 화면 보임 신호) 푸시 대신 화면에만 띄운다.
  - 그 밖에는 맥 배너 + 폰 푸시를 함께 보낸다. 앱 메뉴에서 "폰에 보내기"를 켜고 끈다 (기본 켬). 켜 둬도 위 생략 조건은
    따른다.
  - 맥 앞에 있을 때 폰이 같이 울리지 않게 하는 "자리 비움 판정"(마지막 입력·화면 잠김)은 처음 범위에서 뺀다 (나중 후보).
    써 보고 같이 울리는 것이 거슬리면 넣는다.
  - 컴퓨터마다 자기 조건만 본다. 컴퓨터끼리 서로 알리지 않는다 (동기화 없음).
- 자체 테스트(`DDAK_SELFTEST`)는 지금 알림처럼 보내지 않고 기록한다.

### 안 읽은 수 · 상태를 Rust로 모으기

폰과 데스크톱이 같은 숫자를 보려면 지금 프론트에 있는 것 일부를 Rust로 옮겨야 한다.

- **안 읽은 수**: 프로젝트마다 "사용자가 마지막으로 본 메시지 번호"를 Rust 메모리에 둔다 (지금처럼 앱을 다시 켜면 처음부터.
  저장은 나중 후보). 셈은 지금 `ChatPanel`과 같은 필터: `from != user`이고 `to`에 `user`가 있는 메시지.
  - 데스크톱: 지금 `ChatPanel`이 "보고 있음"(패널 열림 + 그 프로젝트가 보임 + 창이 앞)일 때 `seen`을 올리는 바로 그 자리에서
    Rust에 알린다 (`chat_seen(project, id)`). 그래서 새 메시지가 왔을 때·창이 다시 앞으로 왔을 때도 지금 동작과 같다.
    `set_view`로 추측하지 않는다 (`set_view`는 활성 프로젝트·채팅 패널이 바뀔 때만 온다).
  - 폰: `POST /read`로 올린다.
  - 올라가면 Rust가 프론트에 알려 사이드바·Dock 배지가 폰에서 읽은 것도 반영한다.
- **세션 상태**: 프론트가 `programStatus.ts`로 아는 상태(작업 중·완료·오류·기다림 종류·한 줄 `msg`)를 지금
  `pty_awaiting`처럼 Rust에 알린다 (`pty_status`). 폰은 참여자 칩에 이것을 보인다.

### 폰에서 프로젝트 열기 (M2)

- Workspace는 프로젝트를 처음 열 때 만들어지므로, 앱을 켠 뒤 열지 않은 프로젝트에는 세션이 없다.
- 폰 목록에서 그런 프로젝트를 고르면 "맥에서 열기"를 보인다. 누르면 Rust가 프론트에 이벤트를 보내 그 프로젝트의
  Workspace를 만든다 (지금 사이드바에서 처음 여는 것과 같음: 저장된 탭을 이어서 하기로 복원). 데스크톱 화면의 활성
  프로젝트는 바꾸지 않는다.
- 세션이 채팅방에 참여하면 참여자 이벤트로 폰에 보인다.

### 모바일 화면 (`mobile.html`, `src/mobile/`)

- Vite 진입점을 하나 더 둔다. 같은 `src/i18n`·`themes.ts` 토큰을 쓴다 (새 문구는 사전에 키로, CLAUDE.md 규칙 그대로).
- 화면 셋:
  - **컴퓨터 목록**: 연결한 컴퓨터마다 이름, 켜짐/꺼짐(`/api/info`가 답하는지), 안 읽은 수, 기다리는 세션 수.
    "컴퓨터 추가"(코드·QR), 컴퓨터 이름 바꾸기·빼기. 컴퓨터가 하나뿐이면 이 화면을 건너뛰고 프로젝트 목록부터 연다.
  - **프로젝트 목록** (고른 컴퓨터의): 이름, 안 읽은 수, 열린 세션 수, 사용자를 기다리는 세션이 있으면 강조. 연결 끊김 표시.
    위에 컴퓨터 이름과 다른 컴퓨터로 바꾸는 버튼.
  - **채팅**: 메시지 목록(위로 스크롤해 이전 페이지), 자동 깨우기 멈춤 알림·재개, 참여자 칩(상태·알림 대기) +
    입력란. 칩을 누르면 `@이름 `. 데스크톱 패널과 같은 동작이되 터치용 크기.
- 열릴 때·다시 앞으로 올 때·VPN이 다시 이어질 때 마지막으로 받은 번호 뒤를 다시 읽는다 (모바일 브라우저는 백그라운드
  PWA의 연결을 끊는다).
- 서비스 워커는 푸시 받기와 알림 누르기만 한다. 오프라인 캐시는 두지 않는다 (맥이 꺼져 있으면 쓸 수 없으므로
  "ddak에 연결할 수 없음"을 보인다).
- 화면은 정적 파일로 빌드해 고정 주소(GitHub Pages)에 배포한다 (방식 "가"). 개발 중에는 Vite 개발 서버에서 띄우고,
  ddak의 CORS 허용 출처를 개발 주소로 바꿔 쓴다.

### 설정 화면 · Tailscale 연동 (M4)

- 앱 메뉴 "모바일 연결…" 창:
  - 켜기/끄기, 포트, 이 컴퓨터의 이름 (폰에 보일 이름), 화면 주소 (CORS 허용 출처, 기본은 공식 주소)
  - Tailscale 상태 (`tailscale status --json`: 설치·로그인·MagicDNS 이름·HTTPS 인증서 사용 가능 여부). 없으면 설치·설정 안내.
  - `tailscale serve` 설정: ddak이 직접 실행할지(결정 D5), 아니면 실행할 명령을 보여 주고 복사만 할지.
    정확한 CLI 문법은 M0에서 확인해 적는다.
  - 페어링 QR, 연결된 기기 목록·해제
  - 폰 알림 규칙 (위)
- **잠자기 막기**: "작업 중인 세션이 있으면 유휴 잠자기 막기"(`caffeinate -i`)는 다른 작업그룹(dev-review-9)이 작업 중이다
  (아직 커밋 전). 모바일은 그것만으로는 모자라다: 작업이 끝나 맥이 쉬다 잠들면 폰에서 다음 명령을 보낼 수 없다.
  그래서 "모바일 연결이 켜져 있는 동안 항상 깨어 있기"를 설정으로 둔다 (같은 장치를 쓰고 조건만 넓힘, 화면은 꺼져도 됨).
  덮개를 닫는 것은 막을 수 없다고 창에 적는다.

## 단계

각 단계는 리뷰 1회를 받고 사용자 승인 후 커밋한다.

**구현 순서 (2026-10-27 사용자 결정)**: 맥 1대 + 폰으로 먼저 쓸 수 있게, M1~M4를 아래 세 단계로 다시 묶는다.
맥 B 실험(M0 2·3번의 두 대 부분)은 필요할 때 한다.

| 단계 | 내용 (아래 M 항목에서 가져옴) |
|---|---|
| 1단계 | M1 전부 + M2의 보내기·재개·`via` + M4의 최소 "모바일 연결…" 창 (켜기, Tailscale 상태, `tailscale serve` 실행, 페어링 QR·코드, 기기 목록·끊기) |
| 2단계 | M3 푸시 + 세션 상태(`pty_status`, 권한 확인 대기 표시. M2에서 당김) |
| 3단계 | 안 읽은 수(`chat_seen`), 폰에서 프로젝트 열기, 잠자기 막기, 알림 규칙 설정, 컴퓨터 이름 바꾸기 |

### M0. 실험 (코드 반영 없음)

실제 기기로 먼저 본다. 시험 기기는 **Android (Chrome)**, Galaxy Z Fold7 (Android 17)이다. Android 16 이상이라
OS의 로컬 네트워크 권한이 있는 버전이므로, 1번에서 Chrome 권한과 함께 이 권한이 Tailscale 주소에 걸리는지도 본다. 결과는 `docs/reviews/<날짜>-mobile-spike.md`.

준비:
- 맥(A, B)과 폰에 Tailscale 설치, 같은 계정으로 로그인. 관리 콘솔에서 MagicDNS와 HTTPS 인증서 켜기.
- Tailnet Lock 켜기 (서명 기기는 맥 A), 기기 키 만료 켜기. 새 기기 승인은 Lock과 함께 켤 수 없어 끈다. 맥 B는 맥 A의 서명을 받아 들어온다.
- ACL: 폰 → 맥 443만 허용. 실험 1번 전에 넣어서, 규칙이 있는 상태에서 연결이 되는지도 같이 본다.
- 공개 HTTPS 출처: 실험용 정적 페이지를 올릴 곳 (사용자 승인 필요).
개발 서버가 아니라 실제 공개 HTTPS 출처(GitHub Pages의 시험 페이지)에서, 맥 두 대(A, B)의 `*.ts.net`으로 붙는다.

1. **연결 (가장 먼저, 실패하면 설계가 바뀜)**: 고정 주소의 PWA가 A·B의 API를 CORS로 부를 수 있는지.
   Chrome의 로컬 네트워크 접근(LNA)은 예전 PNA의 미리 보내기 방식에서 권한 방식으로 바뀌었으므로 일반 CORS 성공과 따로 본다:
   권한 처음 허용·거절, 사이트 설정에서 철회한 뒤 복구, PWA 다시 실행, Tailscale VPN 끊김·다시 이어짐.
   안 되면 "단계적 대안"의 Flutter 줄로 가고, Android 앱의 로컬 네트워크 권한이 Tailscale 주소에 걸리는지 같은 항목으로 다시 본다.
2. **컴퓨터 하나가 꺼짐**: A를 끈 상태에서 PWA를 새로 열어 B를 고르고 읽기·보내기가 되는지.
3. **푸시**: 폰이 만든 VAPID 키로 구독하고, 그 개인 키를 가진 A·B가 각각 보낸 Web Push가 모두 오는지. 화면 꺼짐·앱 종료
   상태에서도 오는지, 걸리는 시간. 알림 권한 거절·철회 후 복구. "알림 키 바꾸기" 뒤 예전 키로 보낸 것이 거절되는지.
4. `Tailscale-User-Login` 헤더가 실제로 붙는지, `tailscale serve`의 설정 유지(맥 재시동 후)와 명령 문법.
5. 백그라운드에서 다시 앞으로 왔을 때 `fetch` 스트림 SSE 재연결·다시 읽기.
6. QR → 설치한 PWA로 이어지는 페어링 흐름 (안 되면 PWA 안의 "컴퓨터 추가"만 쓴다).
7. (참고) 서비스 워커 범위를 나눠 구독 여러 개를 만드는 대안이 되는지.

iOS는 지원 대상으로 두되 실기기 확인은 뒤로 미룬다 (16.4+, 홈 화면에 추가해야 푸시, Safari와 PWA 저장소 분리).

### M1. 읽기 전용 + 페어링 (여러 컴퓨터 포함)

- `mobile.rs` 서버, 페어링·기기 토큰, Tailscale 신원·Host·CORS 검사
- `/api/info`, `/api/projects`, `/messages`, `/members`, `/events`
- 모바일 화면: 컴퓨터 목록·추가 + 프로젝트 목록 + 채팅 읽기. 고정 주소 배포(GitHub Actions)
- 처음부터 컴퓨터 여러 대를 전제로 만든다 (하나일 때는 컴퓨터 목록을 건너뛸 뿐). 나중에 붙이면 저장 구조·주소·알림을
  모두 다시 고쳐야 한다.
- 테스트: Rust 단위 테스트(인증 거절 경우들, 페이지 나누기), 자체 테스트 단계 `mobile`(모바일 서버에 HTTP로 붙어 목록·메시지 확인)

### M2. 보내기 + 프로젝트 열기

- `POST /messages` (`Chats::post`, `via` 기록), 칩·멘션, 자동 깨우기 재개
- `pty_status`로 세션 상태 보이기
- 폰에서 "맥에서 열기"
- 테스트: 자체 테스트에서 모바일로 보낸 메시지가 세션을 깨우는지 (지금 채팅 깨우기 시험과 같은 방식)

### M3. 푸시 알림

- 폰의 VAPID 키·구독 받기, `push.rs`, `notify::send`에 폰 경로, 보내기 규칙, 안 읽은 수를 Rust로 (`chat_seen`), 폰의 "알림 키 바꾸기"
- 테스트: 보내기 규칙 단위 테스트 (종류 `Chat`·`Attention` × 창 앞·프로젝트 보임·채팅 패널 열림 × 폰이 보고 있음 조합),
  자체 테스트는 기록으로 확인, 실제 Android로 직접 확인

### M4. 설정 화면 · 잠자기 · 문서

- "모바일 연결…" 창, Tailscale 상태, funnel 경고, 잠자기 막기
- `docs/spec.md`에 "모바일" 절 추가, 사용 안내 (README)

### 나중 후보

- 권한 확인·선택 창에 폰에서 답하기: 화면에 뜬 선택지(이미 화면 판단에서 읽고 있음)를 폰에 버튼으로 보이고,
  누르면 그 키를 터미널에 보낸다. 잘못 누르면 되돌릴 수 없는 승인이 될 수 있어 따로 설계한다.
- 터미널 출력 보기 (읽기 전용, 마지막 N줄)
- 맥 앞에 있으면 폰에 보내지 않기 (마지막 입력·화면 잠김으로 자리 비움 판정)
- 안 읽은 위치를 앱 데이터에 저장 (다시 켜도 유지)
- 폰에서 작업그룹 만들기

## 위험 · 미확인

- Android Chrome의 로컬 네트워크 접근 권한: 공개 출처에서 Tailscale 주소(100.x)로의 요청을 막거나 권한을 묻는다. M0 1번.
- Web Push 전달 신뢰성 (조용히 구독이 끊기는 경우, iOS는 특히). 끊기면 다시 구독 안내를 화면에 둔다.
- `tailscale serve`의 명령 문법·설정 유지 방식은 버전에 따라 다르다. M0에서 지금 버전으로 확인한다.
- 폰에서 보낸 명령이 터미널 입력 중인 창을 깨우는 경우: 지금 깨우기 규칙("3초 입력 없을 때", 초안 뒤에 붙음)을
  그대로 따른다. 맥 앞에 아무도 없으면 초안이 없으므로 문제없지만, 맥에 쓰다 만 초안이 있으면 알림이 그 뒤에 붙는다.
- 메시지 파일 전체 읽기: 방이 커지면 모바일 페이지 요청마다 파일을 다 읽는다. 필요하면 번호 → 위치 색인을 둔다.
- 팀 배포 때 Tailscale 설치를 요구하게 된다. 원하지 않는 팀원은 모바일 연결을 쓰지 않으면 된다 (기본 꺼짐).
- 고정 주소의 화면과 각 컴퓨터의 ddak 버전이 어긋날 수 있다. API 버전을 올릴 때는 화면이 이전 버전도 한동안 지원한다.
- 같은 프로젝트를 두 컴퓨터에서 열면 채팅방·세션이 따로라 폰에 두 번 보인다 (의도한 동작). 컴퓨터 이름으로 구별한다.
