# ddak 스펙

> 최초 작성: 2026-10-21
> 상태: 개발 중 (파일 트리, 다중 터미널, 다국어·테마 완료)

## 배경

VS Code + Claude Code 조합은 대부분의 기능이 불필요하고, 필요한 기능은 없으면서 무겁다.
필요한 기능만 담은 가벼운 개인용 AI 작업 도구를 직접 만든다.

이름 `ddak` = "딱 필요한 것만". 실행 명령어 이름으로도 사용한다.

## 핵심 개념 (2026-10-23 사용자 흐름 기준으로 재정의)

```
작업그룹 구성 (앱 전체 설정, 게임의 "파티" 같은 것)
   예: "개발+리뷰" = [claude: 기획/개발], [codex: 리뷰/QA, 읽기 전용]
   └ 기본 구성 1개 지정

프로젝트 목록 (사이드바)
 └ 프로젝트 (폴더)
    ├─ 저장소 1~N개 (server, app, web, docs …)
    ├─ 작업그룹 1 "원본": 원본 폴더에서 작업      ← 탭 1
    │    ├─ claude 세션                          ← 탭 안 분할 창
    │    └─ codex 세션
    ├─ 작업그룹 2: 새 worktree 세트에서 작업       ← 탭 2
    └─ 채팅방 1개 (모든 작업그룹의 세션 + 사용자)
```

- **작업그룹 구성**: 세션 구성 여러 개의 묶음. 하나를 기본으로 지정한다.
- **세션 구성**: 이름(역할) + 실행 명령 + 인자 + 첫 지시문. ddak은 CLI를 해석하지 않는다.
  읽기 전용·페르소나는 각 CLI의 인자/첫 지시문으로 표현한다 (새 CLI가 와도 코드 수정 불필요).
- **프로젝트**: ddak에 등록한 폴더. 사이드바에 프로젝트 목록이 있고 펼치면 저장소가 보인다.
- **저장소**: 프로젝트 폴더 안의 git 저장소 (`.git`이 있는 폴더).
- **작업그룹**: 프로젝트 안에서 실제로 돌아가는 구성 하나. 화면에서는 **탭 하나 = 작업그룹 하나**,
  **분할 창 하나 = 세션 하나**. 세션 추가 = 그 탭에서 분할.
  - 첫 작업그룹은 "원본": 원본 폴더에서 바로 작업. 닫아도 아무것도 지우지 않는다.
  - 작업그룹을 추가하면 새 worktree 세트를 만든다 (아래 설계).
- **메인 에이전트**: 세션마다 다른 모델을 쓸 수 있다 (동시에 여러 모델 사용이 목표).
- **서브 에이전트**: 각 세션의 에이전트가 자체적으로 사용한다. ddak이 관여하지 않는다.
- **채팅방**: 프로젝트마다 하나. 모든 작업그룹의 세션과 사용자가 참여. 참여자 이름은 `그룹/역할`.

## 작업그룹 · worktree 설계

**worktree 세트**: worktree는 저장소 단위라, 작업그룹 하나에 저장소마다 worktree를 만들고
프로젝트처럼 보이는 폴더 하나로 묶는다. 세션의 작업 폴더는 이 묶음 폴더다
(claude는 작업 폴더와 상위의 CLAUDE.md를, codex는 AGENTS.md를 읽는다).

```
~/.ddak/worktrees/<프로젝트>/<그룹>/
   ├─ server/   ← server 저장소 worktree (브랜치 ddak/<그룹>, 원본의 현재 HEAD에서 시작)
   ├─ web/      ← web 저장소 worktree
   └─ CLAUDE.md, AGENTS.md …  ← 프로젝트 루트의 저장소 아닌 항목은 심볼릭 링크 (그룹 간 공유됨)
```

- 프로젝트 폴더 밖에 둔다. 안에 두면 파일 트리·검색이 지저분해진다.
- 기본은 모든 저장소에 worktree를 만들고, 만들 때 저장소를 고를 수 있다.
- **worktree 준비 명령** (1차 범위): 저장소마다 설정. 새 worktree를 만든 뒤 그 폴더에서 실행한다
  (예: `.env` 복사, `npm install`). 이것이 없으면 새 그룹은 바로 쓸 수 없다.
- 파일 트리는 **보고 있는 탭(작업그룹)의 폴더**를 보여준다. 원본 탭이면 원본, 그룹 2면 그 worktree 세트.
- **그룹 끝내기**: 저장소별 브랜치 상태(커밋 수, 정리 안 된 변경)를 보여주고, 병합/PR은 사용자(또는
  에이전트)가 한다. 병합이 확인되면 worktree와 브랜치를 지운다.
- **복원**: 프로젝트를 다시 열면 기본 구성이 아니라 마지막 상태(그룹·탭·분할)를 복원하고 CLI를
  이어서 실행한다 (예: `claude --continue`). 기본 구성은 처음 열 때와 그룹 추가 때만 쓴다.
- 같은 작업그룹에 쓰기 가능한 세션을 둘 이상 추가하면 경고한다 (같은 파일을 동시에 고칠 수 있음).
  병렬 작업은 그룹 추가로 유도한다.
- 프로젝트 등록·작업그룹 상태는 앱 데이터에 저장한다. 프로젝트 폴더에 표시 파일을 두지 않는다.
- 나중에 저장소를 추가하면 기존 작업그룹에도 worktree를 만들지 묻는다.
- 알아둘 점: 새 worktree 폴더마다 claude·codex가 처음 한 번 폴더 신뢰를 묻는다.
  claude의 대화 기록·메모리는 폴더 경로별로 따로 쌓인다.

## 기능 범위

### 1차 (필수)

1. **프로젝트 목록 + 파일 트리** — VS Code 수준의 파일 탐색. 프로젝트·저장소 폴더를 아이콘으로 구별.
2. **다중 터미널** — 여러 개의 터미널을 동시에 연다.
3. **작업그룹** — 구성(파티)대로 세션을 띄운다. 추가 그룹은 worktree 세트 + 준비 명령.
4. **프로젝트 채팅방** — 세션 간 / 메인 에이전트 간 / 사용자와의 대화.
5. **git graph** — 커밋 그래프 보기. 어떤 세션이 어떤 브랜치에서 작업 중인지 표시하면 좋다.

### 나중에 (필요할 때 하나씩)

- 마크다운 뷰어
- 환경설정 (설정 화면 또는 설정 파일, 터미널 글꼴 등). 그때 지금 localStorage에 따로 있는
  테마·언어·화면 배율도 함께 옮긴다.
- 기타 (diff 뷰어 등)

## 세션 실행 방식 (결정: A)

세션은 **기존 CLI(claude, codex, gemini 등)를 터미널(PTY)에서 그대로 실행**한다.
ddak은 터미널·worktree·채팅방만 제공하고, 에이전트 기능은 각 CLI에 맡긴다.

검토한 방식:

- **A. 기존 CLI를 터미널에서 실행 ← 채택**
  - 파일 편집·권한·서브 에이전트·컨텍스트 관리를 CLI가 이미 제공
  - 구독 요금제(Claude Pro/Max, ChatGPT 등) 그대로 사용, API 토큰 과금 없음
  - CLI 업데이트를 바로 누림
  - 단점: 채팅방 연동이 MCP + PTY 깨우기로 간접적, UI는 CLI의 TUI 그대로
- **B. ddak이 직접 에이전트 루프 구현** — 제외
  - 사실상 Claude Code 재구현으로 작업량이 매우 큼, API 토큰 과금
- **C. CLI를 헤드리스로 실행(예: `claude -p --output-format stream-json`) + 자체 UI** — 보류
  - A의 깨우기 방식이 불편해지면 특정 CLI만 C로 전환 검토.
    터미널 구조를 유지한 채 추가할 수 있다.

## 기술 스택 (결정)

**Tauri 2 + React(TypeScript) 프론트엔드 + Rust 백엔드**

프론트엔드는 Solid와 비교 후 React 채택:
가장 무거운 터미널은 xterm.js가 프레임워크와 무관하게 그리므로 성능 차이는 작고,
파일 트리(react-arborist)·마크다운(react-markdown) 등 생태계, AI 코드 품질,
사용자의 React Native 경험에서 React가 유리하다.

| 기능 | 구현 |
|---|---|
| 파일 트리 | 웹 UI + Rust `notify` (파일 감시) |
| 터미널 | 프론트 **xterm.js** + Rust `portable-pty` |
| worktree | `git worktree` CLI 호출 |
| git graph | Rust `gix`로 커밋/레인 계산 → 프론트에서 SVG/Canvas + 가상 스크롤 |
| 채팅방 | 앱 내장 **MCP 서버** (localhost) + SQLite |

### 선택 이유

- 무거움이 출발점이므로 Electron 제외. Tauri는 OS WebView 사용 → 작은 번들, 적은 메모리.
- 터미널이 핵심. Claude Code 같은 TUI를 안정적으로 그리는 검증된 웹 터미널은 xterm.js (VS Code와 동일).

### 검토 후 제외한 대안

- **Electron**: 전부 TS라 개발은 빠르지만 VS Code와 같은 무거움.
- **Flutter 데스크톱**: xterm.dart의 TUI 렌더링 안정성이 xterm.js에 못 미침.
- **Swift 네이티브**: macOS 전용, UI 개발 비용 큼.
- **UI까지 순수 Rust (GPUI + alacritty_terminal 등)**: 가능은 함 (Zed 사례). 그러나
  - GPUI는 문서 부족·API 변동, egui/iced는 위젯을 직접 만들어야 함
  - 터미널 렌더링·선택·한글 IME·스크롤을 직접 구현해야 함
  - 마크다운/diff/하이라이팅 등 이후 기능의 생태계가 웹에 비해 빈약
  - 컴파일 사이클로 UI 반복 개발이 느림
  - AI가 작성하는 GPUI 코드 품질이 웹 UI 대비 낮음
  - 성능 병목이 생기면 그 부분만 Rust로 내리는 전략을 택함

## 배포 계획 (나중에 하나의 단계로 진행)

- 공개 GitHub 저장소(madsys11/ddak)에서 개발한다. 사용자가 먼저 쓰며 다듬고, 이후 팀원(모두 macOS)에게 배포한다.
  그 전까지는 `npm run tauri build`로 만든 앱을 쓴다 (직접 빌드한 앱은 quarantine이 없어 서명 없이 실행된다).
- 저장소에 개인정보를 넣지 않는다. 커밋 작성자는 GitHub noreply 주소를 쓴다 (이 저장소의 로컬 git 설정).
- `tauri-plugin-updater` + GitHub Actions(`tauri-action`) + GitHub Releases(`latest.json`).
  태그 push → 빌드·서명·공증 → 릴리스 → 앱이 업데이트 확인 후 설치
- 업데이트 서명 키 필요. 개인 키는 GitHub Secrets + 별도 백업 (잃으면 기존 설치본에 업데이트 불가)
- Apple Developer 계정 있음 → 배포 시작부터 Developer ID 서명 + 공증.
  준비물: Developer ID Application 인증서(조직 계정이면 Account Holder만 발급 가능),
  공증용 앱 암호 또는 App Store Connect API 키 → GitHub Secrets
- 앱 식별자는 임시값 `dev.ddak.desktop` (`tauri.conf.json`). 배포 전에 확정한다.
  배포 뒤에는 바꾸기 어렵다 (macOS가 다른 앱으로 인식, 설정·권한이 초기화됨).
- 라이선스는 팀 배포 전에 정한다.
- 버전 번호가 `package.json`, `Cargo.toml`, `tauri.conf.json` 세 곳에 있다. 배포 단계에서 한 곳으로 모은다.

## 채팅방 설계

모델 종류와 무관하게 참여시키기 위해 **MCP**를 사용한다
(Claude Code, Codex CLI, Gemini CLI 모두 MCP 지원).

```
ddak 앱
 ├─ 로컬 MCP 서버 (localhost)
 │    도구: post_message, read_messages, list_members
 ├─ SQLite: 프로젝트 → 채팅방 → 메시지
 └─ 터미널 세션들
      ├─ [claude] server 워크트리  ─┐
      ├─ [codex]  web 워크트리     ─┼─ MCP로 같은 채팅방 접속
      └─ [gemini] docs 워크트리    ─┘
```

- **깨우기 문제**: CLI 에이전트는 스스로 채팅방을 확인하지 않는다.
  새 메시지가 오면 ddak이 해당 세션의 PTY에 알림 문구를 입력해 에이전트를 깨운다.
  ddak이 터미널을 직접 소유하기 때문에 가능하다.
- 사용자는 채팅방 UI에서 직접 메시지를 쓴다.

  - 테마: 다크(VS Code Dark Modern), Solarized Light(사용자가 VS Code에서 쓰는 베이지 테마).
    색은 VS Code 앱 안의 테마 파일에서 가져왔다. 정의는 `src/themes.ts` (UI 색 토큰 + 터미널 색).
    예외: Solarized 터미널 선택색은 테마 값(#EEE8D5)이 배경과 거의 같아 목록 선택색을 반투명으로 썼다.
  - 전환: 보기 메뉴 > 테마 / 언어. 선택은 localStorage에 저장 (설정 파일은 필요해지면).

- 2026-10-23: 프로젝트 목록 (작업그룹 구현 1단계)
  - 사이드바 = 프로젝트 목록. 펼치면 그 폴더의 파일 트리. 저장소(`.git` 폴더)와 worktree(`.git` 파일이
    `.git/worktrees/`를 가리킴) 폴더에 아이콘. 서브모듈은 저장소로 본다.
  - 목록은 앱 데이터 폴더의 `projects.json` (`src-tauri/src/projects.rs`). 프론트가 내용을 정하고 Rust는
    읽고 쓰기만 한다. 파일을 못 읽으면 저장하지 않는다 (빈 목록으로 덮어쓰지 않게).
    자체 테스트는 `DDAK_DATA_DIR`로 따로 둔다 (없으면 저장을 거부).
  - 프로젝트마다 Workspace(탭·분할)가 따로 있다. 처음 열 때 만들고, 다른 프로젝트로 옮겨 가면 숨기기만
    한다 (셸 유지). 단축키는 보이는 프로젝트만 받는다. 열린 프로젝트를 목록에서 빼면 확인 후 터미널을 닫는다.
  - 폴더가 사라진 프로젝트는 취소선으로 표시하고 열지 않는다 (목록에서 빼기만 가능).
  - 이전의 단일 폴더(localStorage `ddak.root`)는 쓰지 않는다.

- 2026-10-23: 저장소 추가 + 파일 트리 자동 갱신
  - 프로젝트 행의 `+` → 저장소 추가 창. **URL에서 clone** 또는 **로컬 저장소 연결**(프로젝트 안에 심볼릭 링크).
    로컬 저장소를 프로젝트 안으로 옮기는 방법은 두지 않는다 (실행 중인 저장소가 끊길 수 있음).
    `src-tauri/src/repos.rs`. 오류는 코드로 돌려주고 문구는 사전 `repo.error.*`.
  - clone은 물어볼 터미널이 없어서 `GIT_TERMINAL_PROMPT=0`, ssh `BatchMode=yes`로 묻지 않고 실패하게 했다.
    비밀번호·호스트 키 확인이 필요한 저장소는 터미널에서 한 번 clone 해야 한다. clone 중 취소는 아직 없다.
  - 파일 트리 자동 갱신: 펼쳐진 폴더만 하위 제외로 감시 (`notify`, macOS는 FSEvents. `src-tauri/src/watch.rs`).
    FSEvents는 링크를 따라간 실제 경로로 이벤트를 주므로 실제 경로 → 트리 경로로 바꿔 보낸다.
    접히지 않은 폴더 안의 `.git`이 생기면 그 폴더의 저장소 아이콘을 갱신한다. 접힌 폴더 안에서 나중에
    `.git`이 생기는 경우는 폴더가 만들어질 때 한 번 읽은 결과에 달려 있다 (clone·git init은 바로 생겨서 문제없음).
  - 트리에서 링크는 이름 뒤 ↗, 마우스를 올리면 가리키는 경로.

- 2026-10-23: 새 파일·폴더
  - 트리 오른쪽 클릭 → 새 파일 / 새 폴더 (VS Code처럼 그 자리에 이름 입력란, Enter 생성, Esc·다른 곳 클릭 취소).
    파일을 오른쪽 클릭하면 그 파일이 든 폴더에 만든다. 프로젝트 행의 `+`는 새 파일·새 폴더·저장소 추가 메뉴.
  - 메뉴는 네이티브 팝업이 아니라 화면 안에 그린다 (`src/ContextMenu.tsx`, 자체 테스트가 누를 수 있게).
  - 이름 검사(빈 이름, `/`, `.`, `..`, 이미 있음)는 저장소 추가와 같은 함수 (`fs.rs`의 `child_path`).
    `a/b/c.txt`처럼 중간 폴더까지 만드는 것은 아직 안 된다. 이름 바꾸기·삭제도 아직 없다.

- 2026-10-23: 화면 배율
  - 보기 메뉴 > 확대 ⌘= / 축소 ⌘- / 실제 크기 ⌘0. 웹뷰 배율(`setZoom`)이라 사이드바·탭·터미널·오른쪽 클릭
    메뉴·대화상자가 같이 커진다. 단계 0.5~2배 (`src/prefs.tsx`의 `ZOOM_LEVELS`), localStorage에 저장.
  - 화면 위 메뉴 막대는 macOS가 그려서 바뀌지 않는다 (VS Code도 같음).
  - ⌘+는 Shift+=라 메뉴 단축키를 ⌘=로 걸었다. 자체 테스트는 메뉴 항목 실행이라 실제 키 입력은 직접 확인 필요.
  - **터미널 번짐** (사용자 보고, 2배에서 터미널만 흐림): WKWebView 배율은 Chromium과 달리 devicePixelRatio를
    바꾸지 않는다. 실험: 배율 1.1에서 dpr 1 그대로, 터미널 캔버스 875px(필요 962px) → 늘어나서 번짐.
    `src/zoom.ts`가 devicePixelRatio를 (실제 값 × 배율)로 돌려주게 했다. xterm은 resize 때 이 값을 다시 읽어
    다시 그린다 (`CoreBrowserService.ts`). 자체 테스트가 캔버스 해상도 = CSS 크기 × 배율 × 화면 비율을 확인한다
    (수정을 끄면 실패하는 것도 확인).
  - **터미널 아래 검은 띠** (같은 보고): 줄 단위로만 채워져 마지막 줄 아래 남는 공간이 `.xterm-viewport`인데,
    `xterm.css`가 이 배경을 `#000`으로 고정해 둔다. 배율이 클수록 줄이 높아 띠가 커진다.
    테마의 터미널 배경색(`--terminal-bg`)으로 덮었다.
